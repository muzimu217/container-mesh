## 1. 产品是什么

**container-mesh（cmesh）**：用户态组网工具。把散落各处的机器——云服务器、家里
的电脑、公司的容器、无公网 IP 的沙箱——组成一张**私有 mesh 网络**。装上后设备
之间互相发现、互传文件、互发消息、互执行命令、互测延迟，如同插进同一台交换
机——但零开端口、零 root、零第三方。

一句话定位：**一张跟着你的容器到处走的局域网。**

## 2. 解决的痛点

| 痛点 | 现状 | cmesh 的回答 |
|---|---|---|
| 容器/云主机互通 | 开安全组、端口映射、分发 SSH 密钥 | 能出站即能入网，零入站端口 |
| 受限容器（无 root/无网络特权） | VPN/K8s 插件全部装不上 | 纯用户态单二进制，无特权要求 |
| 信任第三方 | 商业工具要注册、流量过厂商 | 无云端注册、锚点自托管、数据面点对点 |
| 装配成本 | 证书/CA/域名/配置半天 | 一条命令入网，设备私钥即身份（mTLS） |

## 3. 目标用户

1. **开发者/运维**：多台散落 VPS/NAS/家庭服务器/容器想要内网式互通，不想开端口
2. **AI Agent 基础设施**：多个 agent 容器互传产物、互调命令——私有 mesh 即神经网
3. **个人私有云**：所有设备连成一张网，一个入口看全部（后续：一人多网、多网共服）
4. **受限环境用户**（竞品盲区）：CI 沙箱、Serverless、无特权容器

## 4. 产品气质关键词

**私有 · 自主 · 随时在线**。目标感受："我的设备们彼此认识，我随时看得见它们全
部"——安全感与掌控感，而非极客门槛。中文用户为主。

## 5. 前端要承载的信息需求

1. 首屏第一眼：这张网有多少设备、几台在线（产品最核心的数字）
2. 谁是谁：设备身份、可达状态、地址入口；**离线是正常状态**（保留、不除名、不红）
3. 网的活性：数据自动刷新（真实接口轮询）；节点失联有明确提示，不白屏
4. 生长空间：后续挂传输/命令入口、多网络切换

## 6. 硬约束（任何设计必须满足）

- 单文件 HTML，零外部依赖（CDN/字体/框架都不行）——要在完全离线的容器里渲染
- 所有数字来自真实数据接口（`/api/mesh`），无演示数据路径
- 中文界面；v1 只读为主
- 交付物会被 `go:embed` 进单个 Go 二进制，由发现节点在 `/panel` 伺服

## 7. 产品定位与设计结论

### 7.1 产品不是“网络工具后台”

cmesh 的核心对象不是端口、证书或日志，而是**一张正在运行的私有设备网络**。用户进入产品时首先要回答的不是“用了什么协议”，而是：

- 我的网络现在有几台设备？
- 哪些设备此刻可用？
- 哪台设备可以传文件、发消息或执行操作？
- 某台设备为什么不可用？
- 我是否仍然拥有这张网络的控制权？

因此，界面必须以“网络状态和设备关系”为中心，技术细节作为可展开的证据，而不是首屏主角。

### 7.2 学术派不是冷漠或难用

产品希望有学术派的可信度，但不能做成论文阅读器或工程师终端。建议采用：

- **严谨**：状态、时间、版本、来源、网络边界清楚可追溯
- **克制**：少装饰、少营销话术、少无意义动画
- **友好**：用户先看到结论，再按需展开证据
- **可解释**：每个异常都有原因、影响和下一步动作
- **稳定**：布局、术语、颜色和交互行为长期一致

核心气质定义：**研究仪器的严谨度，日常工具的易用性。**

## 8. 推荐的整体风格

### 8.1 视觉关键词

**学术基础设施、私有控制台、安静、清晰、可信、可验证、长期耐看。**

避免以下方向：

- 不做赛博朋克、霓虹发光、代码雨、终端黑客风
- 不做营销官网式的大渐变、超大英雄图、装饰性玻璃卡片
- 不做过度游戏化的积分、徽章、彩色状态墙
- 不把“AI”作为主视觉，不用机器人、脑网络或神经元插画代表产品
- 不把离线设备设计成红色故障；离线是网络状态，不等于安全事故

### 8.2 色彩策略

建议采用**中性底色 + 单一可信强调色 + 少量语义色**：

- 页面底色：偏中性的冷白或深灰，不使用大面积纯黑
- 主要文字：高对比但不刺眼
- 次要文字：用于时间、地址、协议和解释，不降低关键字段可读性
- 主强调色：蓝青或深青，用于选中、链接、可信操作和网络关系
- 在线：绿色，仅表达“当前可达”
- 离线：中性灰，表达“当前不可达但仍属于名册”
- 警告：琥珀色，表达“需要关注但不一定是故障”
- 错误：红色，仅用于请求失败、权限拒绝、配置错误或危险操作

颜色不能单独承载语义。状态必须同时使用文字、图标或形状表达。

### 8.3 字体与信息密度

- 普通中文使用清晰的系统无衬线字体
- device ID、地址、版本、时间戳和命令使用等宽字体
- 数字使用等宽或表格数字，方便比较变化
- 不使用极小字体隐藏技术信息；次要信息仍须可读
- 信息密度偏高，但每个区域只服务一个问题
- 不用负字距，不用随视口缩放字体

## 9. 信息架构

### 9.1 v1 的页面结构

v1 不需要复杂后台，建议采用单页控制台，结构固定为：

1. **顶部产品栏**
   - cmesh 标识与当前网络名称
   - 当前账号/网络身份的简短标识
   - 数据时间、刷新状态、连接发现节点状态
   - 预留网络切换入口，但没有多个网络时不要显示空菜单

2. **网络总览区**
   - 首要数字：`在线设备 / 名册设备`
   - 网络版本或最后变更时间
   - 当前发现节点/锚点状态
   - 一句短状态结论，例如“网络正常，4/5 台设备在线”

3. **设备列表区**
   - 设备状态
   - 设备 ID 或用户设置的显示名称
   - 设备角色：锚点、本机、普通成员
   - 公告端点
   - 最后在线时间
   - 可展开的状态解释

4. **状态解释区**
   - 只在出现异常、最近发生变化或用户选中设备时出现
   - 说明数据时间、失败原因、重试状态和影响范围
   - 不能用一整页日志替代解释

5. **后续能力入口预留区**
   - 文件传输
   - 消息
   - 命令/远程操作
   - 延迟测试
   - 网络设置

这些入口在 v1 可以是未启用或只读状态，但不得伪装成已经完成的功能。未完成入口应明确标注“即将支持”或暂不显示。

### 9.2 v1 不建议加入的内容

- 不在首页展示完整证书、公钥、TLS 握手细节
- 不在首页展示原始日志、Send-Q、重试堆栈
- 不加入没有真实数据源的拓扑动画
- 不展示“网络质量评分”这类未经定义的综合分数
- 不加入虚构的地理地图、流量热力图或成员排名

技术证据可以放在设备详情或“诊断”区域，但必须从用户问题出发。

## 10. 核心用户流程

### 10.1 第一次打开

用户应该在 5 秒内完成三件事：

1. 知道当前是否连接到了发现节点
2. 知道网络中有几台设备、几台在线
3. 知道下一步可以对哪台设备进行操作

首次没有数据时不要展示假成员。应展示明确的空状态：

- 发现节点尚未连接：说明正在连接，并给出重试状态
- 网络只有本机：说明网络已建立，但还没有其他成员
- 成员存在但离线：说明成员仍在名册中，当前不可达

### 10.2 查看设备

点击设备后，显示一个轻量详情区域，而不是跳转到复杂新页面。详情包含：

- 显示名和 device ID
- 当前状态及状态来源
- 公告端点
- 最后在线时间
- 名册版本
- 本机与该设备之间可用的动作
- 若不可用，给出具体原因和建议

### 10.3 加入网络

未来的自动加入流程必须围绕“凭证/加入码”设计，但 v1 不应把流程硬编码成视觉形式。设计应预留：

- 加入某个网络
- 当前网络身份
- 凭证状态
- 凭证过期、撤销或权限不足
- 一台设备加入多个网络

这些概念要能扩展到多租网，但当前没有多个网络时不提前制造复杂度。

### 10.4 节点失联

节点失联时必须保留最后一次有效快照，并同时显示：

- 数据最后更新时间
- 当前连接状态
- 自动重试状态
- “这是缓存数据，不代表当前实时状态”的明确提示

恢复后自动更新，不要求用户刷新页面，也不应突然重排整个页面。

## 11. 术语规范

统一使用以下用户可见术语：

| 技术概念 | 推荐显示 | 说明 |
|---|---|---|
| membership | 网络成员/名册 | 是否属于这张网络 |
| liveness | 在线/离线 | 当前是否可达 |
| announcement | 公告端点 | 设备对外提供的可连接地址 |
| discovery node | 发现节点 | 负责发现和推送成员视图 |
| anchor/relay | 锚点/中继 | 按具体能力显示，不混为同一概念 |
| endpoint | 连接地址/公告端点 | 不直接把 endpoint 丢给普通用户 |
| device ID | 设备 ID | 可复制，可作为高级信息保留 |
| account | 网络账号/网络身份 | 避免让用户误解为厂商云账号 |

禁止用“掉线=删除”“已批准=已经可拨通”“有端点=一定在线”等混淆状态的文案。

## 12. 交互原则

1. **结论先行**：先显示“4/5 台在线”，再允许查看证据
2. **状态可解释**：任何黄色/红色状态都说明原因、影响和下一步
3. **不打断工作**：自动刷新不应让列表跳动、滚动位置丢失或详情关闭
4. **动作有边界**：v1 只读；未来执行命令、传输文件和凭证管理必须明确目标和权限
5. **复制友好**：device ID、地址、命令、加入码都应方便复制
6. **渐进披露**：普通用户看到简洁状态，运维用户可以展开诊断细节
7. **可恢复**：失败提供重试、复制诊断信息或返回上一步的路径
8. **可键盘操作**：焦点顺序、表格行、详情和按钮都应可访问
9. **响应式**：桌面用于管理，移动端用于快速查看；移动端不追求完整日志

## 13. 设计交付物的边界

设计方第一阶段不要直接画完整原型，也不要假设不存在的后端能力。先交付：

1. 产品视觉方向说明：色彩、字体、间距、圆角、阴影、状态语义
2. 信息架构图：顶部栏、网络总览、设备列表、详情、诊断、未来入口
3. 三个关键状态的线框：正常在线、部分离线、发现节点失联
4. 关键组件规范：设备行、状态标签、数据更新时间、告警条、空状态、详情抽屉
5. 组件状态表：默认、悬停、聚焦、加载、空数据、错误、离线、恢复
6. 中文文案规范：成功、等待、失败、重试、批准但尚未可拨等边界状态
7. 对真实数据的假设清单：每个数字来自哪个接口字段，禁止设计方自行造数据

第二阶段才做高保真原型；第三阶段才做单文件 HTML 和 Go 集成。

## 14. 设计验收标准

- 用户首次打开 5 秒内能知道网络规模和在线数量
- 在线、离线、缓存、连接失败、批准未可拨等状态不混淆
- 页面没有依赖装饰性动画或假拓扑图传达产品价值
- 没有真实数据时不显示虚构数字
- 设备详情能支持复制和下一步操作
- 视觉有学术基础设施的可信度，但普通开发者不需要阅读论文才能使用
- 设计能扩展到多网络，但单网络 v1 不被多租网复杂度污染
- 最终页面支持单文件、离线、零外部资源和 Go 单二进制嵌入

## 16. 当前产品事实边界

截至本简报编写时，cmesh 已完成核心用户态组网、设备发现、消息、文件传输、白名单远程操作和延迟测量的多环境验证；前端面板、统一凭证自动加入、正式二进制分发和一机多网仍属于后续产品化工作。设计方案必须明确区分“已实现”“正在开发”和“未来预留”。

当前 main 分支只在成品版本完成后更新；develop 分支用于持续开发和验证。设计稿不应把 develop 实验状态伪装为正式发布能力。
