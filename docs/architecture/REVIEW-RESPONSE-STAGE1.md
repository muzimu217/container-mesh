## 1. 记录 512 KiB → 32 KiB（**接受，已改**）

### 评审说对了什么

> 512 KiB 的单记录在慢链路上会形成严重的队头阻塞，把一条连接的交互延迟拉满。

这是对的，而且我原来的推理确实错了。原设计写的是「512 KiB 比 64 KiB 快 2.5 倍
（539.3 vs 211.9 MiB/s），所以取 512 KiB」——但那两个数字都是**回环**测出来的，
优化目标选错了。

### 量化

记录泵必须收齐整条记录、通过 AEAD 认证，才能交给 yamux 分发。所以一条记录在
链路上要传多久，就是同一连接上其他流的**延迟下限**：

| 记录大小 | 2 MiB/s 链路上的队头等待 | 回环固定开销占比 |
|---|---|---|
| 16 KiB | 7.8 ms | 6.4% |
| **32 KiB** | **15.6 ms** | **3.2%** |
| 64 KiB | 31.3 ms | 1.6% |
| 512 KiB | **250 ms** | 0.2% `[实测]` |

一边 `scp` 传大文件、一边在同一隧道里敲 SSH，512 KiB 会让终端明显卡顿。

### 吞吐怎么补回来

AEAD 从来不是瓶颈：**32 KiB 记录实测仍有 1408 MB/s**。512 KiB 买到的吞吐改由
写侧批量补回——512 MiB 用 512 KiB 记录是 1024 次写；用 32 KiB 记录、每 16 条
合并一次写，**也是 1024 次写**，而延迟下限小了 16 倍。

写入合并因此从「可选」升级为**必须**：不合并的话，缩小记录会把 syscall 数量放大
16 倍，正好把买到的延迟还回去。

### 一处我必须诚实说明的边界

C1 混沌测试的原始判据「2 MiB/s 链路打满时 P99 ≤ 40 ms」**不可判定**：一条被单个
大流打满的 FIFO 字节流上，交互请求必然排在整队数据之后，此时 P99 由队列深度决定
（1 MiB 缓冲 ≈ 500 ms），与记录大小无关。任何记录大小都过不了。

所以 C1 改成：文件传输限到 1.2 MiB/s（留 40% 余量），并加**对照组**——同样场景下
把 `RecordSize` 设回 512 KiB，P99 必须明显更差（≥ 2×）。对照组才是「32 KiB 有用」
的证据。

**打满时大文件会挤占交互流量这件事，如实写进 README**：这是单流 FIFO 的固有性质，
不是记录大小的 bug。彻底解决要给控制流做优先级队列，属于阶段 2 之后（风险 X13）。

## 2. `ErrTransportSwitched` 与 yamux（**接受，且比评审描述的更严重**）

### 评审的担心

> `ErrTransportSwitched` 在 mux 下会让 yamux 看到 EOF 或错乱，导致会话崩溃。

### 实测：比「崩溃」更糟——是静默丢字节

我写了 `TestPartialRecordAcrossSwitchIsLost`：在一条记录的中途触发切换，
测试读到 **24/49 字节**后连接关闭，剩余 25 字节**再也不会到达**。

原因：记录泵把字节流切成记录，而切换会丢弃旧连接上在途的字节。半条记录永久损坏，
`secure.OpenFrame` 的下一个帧与计数器/字节边界都不对齐，必然解密失败，`fail()`
关掉两端，**所有 yamux 流同时断掉**。所谓热切换退化成「切换即断连」。

### 设计改动

| 模式 | 切换语义 |
|---|---|
| 单流（现有 `send`/`recv`） | 允许，行为不变（帧边界清晰，最多丢一帧，上层重传） |
| **mux（`cmesh forward`）** | **建连后锁定路径**。P2P 打洞只在 `StartMuxed` 之前尝试；一旦 mux 跑起来，`Switch` 返回错误而不是替换连接 |

代价明确：mux 会话的生命周期内路径不变。路径真的坏了，会话失败、上层重连
（`Node.Run` 已经会重建 session），而不是假装能无损迁移。

真正的无损迁移需要在记录泵之下加一层带序列号与重传缓冲的虚拟会话层，
那是阶段 3 之后的事，不在阶段 1 的范围内。**我不打算为了「看起来支持热切换」
而在阶段 1 埋一个会静默丢字节的路径。**

## 3. 能力协商（**确认已覆盖，无需改动**）

评审要求「必须有能力协商，不能靠版本号」。设计 §3.4 与 §5 已经规定：

- hello payload 新增 `caps: ["mux","forward"]`，双方取交集
- `wire.Version` **保持 1**（不升到 2）。帧格式完全没变，新帧类型是纯增量，
  `readPump` 的 `default` 分支本来就忽略未知类型；升版本会让 `exchangeHello`
  直接返回 `ErrProtocol`，使现有 `send`/`recv` 在新旧二进制之间立刻不可用
- 对端无 `mux` 能力时明确报错：`"peer does not support forwarding; upgrade both sides"`，
  **不静默降级**成「能连但转发不工作」

测试用例 I13 覆盖这条：`forward` ↔ `send` 必须明确报错。

## 4. 内存与半关闭泄漏（**部分已覆盖，已补强**）

### 原有设计

| 机制 | 值 | 作用 |
|---|---|---|
| `MaxStreams` | 256 | 并发流上限，被 128 MiB 预算自动压低 |
| 预算公式 | `MaxStreams = min(--max-streams, StreamBudget/(2*Window))` | 256 KiB 窗口 → 256 流；1 MiB → 64 流 |
| `StreamCloseTimeout` | 60 s | 半关闭后等对端 FIN 的上限 |
| 记录泵队列 | 每方向 1 MiB，**有界阻塞** | 满时阻塞写侧，不丢弃 |

### 评审指出后补上的两处

**① EOF 后的拆除期限（`--pipe-drain` 5 s）**

双向 `io.Copy` 里一侧读到 EOF 后，给另一侧 5 s 把剩余数据送完；超时直接 `Reset()`。
没有这条，对端不主动关连接时 goroutine 与 2×窗口 会永久残留。

**② 半开连接的两层防线**

这条在评审前设计里**根本没有**，是真正的缺口。`-L` 的 listener 每条 TCP 连接都会
开一条 mux 流，若对端连上就不说话（端口扫描器、健康检查、`nc` 后忘了打字），
流会一直挂着：

| 防线 | 参数 | 挡什么 |
|---|---|---|
| 第一层 | `--max-pending=128` | 已 accept 但还没拿到 mux 流的本地连接，超出直接关 TCP |
| 第二层 | `--handshake-timeout=10s` | 拿到流但不发 preamble 的对端 |

C3 混沌测试**分别断言这两层**，不能只测一层。

## 5. 体量：5300 行是否过度设计（**部分接受**）

### 接受的部分

评审建议的三处都照做了：

| 项 | 处理 | 节省 |
|---|---|---|
| `allow.go` 210 行（CIDR + 主机名解析 + TOCTOU 一次做完） | 拆开：PR #2 只做主机+端口精确匹配，CIDR 推到 PR #3 | −80 |

| `manager.go` 230 行 | 收到 150 行 | −80 |
| `cli/forward.go` 340 行 | 收到 300 行（去掉只为测试存在的生命周期封装） | −40 |
| `limits.go` 100 行四合一 | 重写为 60 行 | −40 |

总量：**2,575 → 2,275 行生产 / 2,750 → 2,460 行测试**，拆成 3 个可独立合并的 PR。

### 未接受的部分：限流不能删

评审把「令牌桶限流」也归为阶段 1 的越界功能。**这一条我保留，理由是安全性：**

`MaxStreams` 限的是**并发**，不限**速率**。攻击者可以在 256 条流里每秒建/关上千次，
内网扫描的速率完全不受约束——§5.3 攻击场景 2（「端口扫描内网：快速尝试 1000 个
`host:port`」）与安全测试 S8 都依赖这一层。删掉它等于为凑行数削弱一道真实防线。

所以保留限流，但把它从 100 行的四合一模块（限流 + 超时 + 寿命 + 配额）重写成
**60 行的手写令牌桶 + 三个超时字段**，不做配额/寿命/突发平滑那些阶段 1 用不到的机制。

### 未接受的部分：800–1,200 行的估算不成立

评审估「yamux 包装 + 记录泵（60–120 行）+ `-L`/`-R` + 端口白名单 ≈ 800–1,200 行」。
逐项对一下，差额集中在三处，**都不是抽象层**：

| 评审的估算 | 实际 | 差额来源 |
|---|---|---|
| 记录泵 60–120 行 | **280 行** | 评审按「一条 `io.Copy` 加个信封」估的。实际要同时承担：① 引导期直通（hello/p2p 协商还在裸帧上跑）与复用期封 record 两种模式；② `FrameMuxStart` 双向屏障（两端都发出才能切，屏障前到达的非 mux 帧要丢弃而不致命）；③ 两个方向各有界阻塞队列 + 单 drainer；④ 保留 `ErrTransportSwitched` 分支，否则 `--p2p` 升级会当场杀死会话。少任何一条都会破坏现有功能 |
| `internal/mux` 未单列 | **350 行** | 评审把「用 yamux」当成零成本。实际要有：`Config` 与内存预算换算（否则 256 流 × 512 KiB 窗口 = 128 MiB 直接爆）、流数信号量、kind 路由、`CloseWrite` 映射、`LogOutput` 显式接管（yamux 默认写 `os.Stderr`，会污染 CLI 输出） |
| `peer.Session` 改造未计入 | **150 行**（含 `frameconn.go`） | 把 `conn`+`sec` 两个字段换成 `FrameConn` + `Pump`，是**改现有 1138 行文件的核心结构**，不是加个适配器。评审的估算里这一项是 0，但它恰恰是回归风险最高的地方（风险 X4） |

**如果还要再砍，唯一的办法是把 `-R` 整个移出阶段 1**（省 540 行，降到约 1,735）。
但那等于承认「只能从本端拨出去，不能被拨进来」，而 `-R` 正是「让没有公网 IP 的
容器对外提供服务」这个核心场景。

**行数不是验收指标，C1–C4 与 G1 才是。** 我不打算为让数字好看而砍掉核心能力。

## 6. 四项混沌测试（**接受，已写入 §6.5，并补了判据细节**）

| 编号 | 场景 | 判据 | 对应质疑 |
|---|---|---|---|
| **C1** | 2 MiB/s 链路 + 混合流量（1 条大文件限速 1.2 MiB/s + 8 条交互） | 交互 P99 ≤ 40 ms，无一条 > 200 ms；**对照组**（512 KiB 记录）P99 必须 ≥ 2× 更差 | 质疑 1 |
| **C2** | 慢读者：对端开流不读，本端持续 `Write` | RSS 增量 ≤ 50 MiB；`Write` 阻塞而非吃内存；恢复后字节精确 | 质疑 4 |
| **C3** | 500 条半开连接，不发任何字节，30 s 后 RST | ① 第 129 条起被 `--max-pending` 关掉；② 余下 128 条在 `--handshake-timeout` 后清理；③ 30 s 后 goroutine 回落基线 ±10；④ 正常连接 P99 不受影响 | 质疑 4 |
| **C4** | P2P 切换：100 MiB 传输到 30 MiB 时打断直连 | 单流模式：传输继续完成、SHA-256 一致；mux 模式：`Switch` 明确报错、会话失败并给可读原因。**卡住 > 60 s 算失败** | 质疑 2 |

三条实现要点：

1. **C1 的限速必须作用在记录泵之下**（transport 层），否则测的是应用层不是链路。
2. **C3 的两层防线分别断言**，不能只测一层然后推断另一层。
3. **C4 的两个分支分别断言**，不能只测单流然后推断 mux。

全部在 PR #3 合并前的决策门 G1 上跑，结果写回文档。

## 8. 仍然存在的、评审没有提到的问题

如实列出，避免「答复完就万事大吉」的错觉：

1. **`p2p2` 是死代码。** 2283 行生产 + 1847 行测试，`grep -rln "internal/p2p2"`
   在它自己目录外没有任何命中。它的命运（保留为研究物 / 接入 / 删除）尚未决定，
   而它恰好是「记录泵之下加序列号重传层」这个未来方案的参考实现。
2. **`-R` 的端口白名单只约束端口，不约束「谁能触发」。** 持有 code 的人都能请求
   绑定白名单内的端口。阶段 1 的缓解是「零值拒绝 + 审计日志」，不是身份认证。
3. **P2–P5 的性能门槛目前是 `[推断]`。** 实现后第一次实测必须替换成真实数字，
   不能沿用推断值冒充验收。
4. **没有真实多跳 NAT 环境的验证。** 现有 P2P 结论来自 loopback 与 hairpin。
