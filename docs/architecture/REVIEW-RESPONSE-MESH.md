## 一、图（重点评审部分）

### 1. mesh.png 的三处 — **全部接受，已修**

**① S1/S2 标签缺失** ✅ 成立。两个云服务器节点文字完全相同，而连线标注
「经 S1 中转」引用了 S1——读者需要顺着线反推谁是 S1。已改为
`☁️ 云服务器 S1` / `☁️ 云服务器 S2`，并给其余节点加了名字
（laptop / pod-1 / nas），让连线标注有明确落点。

**② K8s Pod → S2 画成中转** ✅ 成立，而且是三处里最实质的错误。
受限容器缺的是**入站端口和 TUN**，出站连任何公网 IP 都行——所以 Pod→S2
应该和 Pod→S1 一样直连。真正互相不可达、需要中转的是**两个都在 NAT 后的**
节点。已改：直连 = laptop↔S1、S1↔S2、pod↔S1、nas↔S1（后两者是出站到公网 IP）；
中转 = laptop↔nas、pod↔nas（两个内网节点经 S1）。

**③ 发现节点画在网边界外** ✅ 成立。它被画在「同一个身份下的网」黄框之外，
视觉上暗示需要外部第三方。已移入框内并标注「S1 兼任」——它是个角色，不是组件。

### 2. stack.png 的四处 — **三处接受一处更正**

**④ 层号重复** ✅ 成立。图中出现两个 `③`（路由与端到端加密），
而 DESIGN.md 定义四层。已按「3a 路由 / 3b 端到端加密」改为同层的两个子层，
全图统一为 ⓪①②③④。

**⑤ yamux 与 E2E 的复用关系未厘清** ✅ 成立，**这是全部评审意见里最有价值的一条**。
如果 yamux 只在每跳（第 2 层），A 与 C 之间的并发流就没有端到端的复用与流控；
如果中转节点解开 yamux 再转发，流结构就暴露给它。原文确实没有回答这个问题。

修法（已写入 MESH-DESIGN §2.3）：**e2e.Session 本身是一条字节流，其内再跑一层
yamux**。中转路径上：`[应用流] → yamux(e2e) → E2E AEAD → yamux(干线,A–B) → yamux(干线,B–C)`。
B 只看到一条干线流载着不透明字节，A↔C 的流结构在密文里。
代价是多一层复用头；如果 MP-2/MP-3 实测不达标，退路是 `FrameMeshData` 帧头
显式 StreamID+窗口（记为风险 X8）。

**⑥ 三重加密威胁 200 MiB/s** ✅ 成立。E2E + 逐跳 SPAKE2 + QUIC TLS = 用户态两遍
AES-GCM。**已明确否决叠加**（MESH-DESIGN §2.3）：组网会话从建立起只有一层用户态
AEAD（E2E），QUIC TLS 是传输层自带、走硬件加速、无法旁路。SPAKE2 只存在于
阶段 1 兼容路径，两条路径不混用。

**⑦ 「心跳 30s」与详设的 10s/30s 矛盾** —— **不实，但暴露的真问题更严重**。

核对结果：`grep -n "10.*HEARTBEAT\|心跳"` 在 MESH-DESIGN.md 里**没有任何心跳参数**
（评审所引的「10s 发送 / 30s 超时状态机」在该文档中不存在）；实际参数写在
DESIGN.md §2.2：**心跳 30 s / 超时 90 s**——比评审以为的还要差 3 倍。

所以：引用错了，方向对了。真矛盾是 P-5 要求 <10 s 而 DESIGN.md 写 90 s。
修法（见下一条）。

## 二、文档交叉问题

### ⑧ 拓扑收敛时间矛盾 — **接受，已修**

按评审建议的第二种思路改（区分优雅/异常），但机制不同：

| 情形 | 机制 | 时限 |
|---|---|---|
| 优雅下线 | 显式 LEAVE 广播 | ≤ 3 s |
| **异常掉线** | **传输层断连检测**（QUIC 空闲超时 / 连接关闭事件，节点上报发现节点） | **≤ 10 s** |
| 挂死未断连 | 心跳超时 | 90 s（兜底） |

**为什么不采纳「3 s 心跳 / 9 s 超时」**：节点与发现节点、与对端本来就保持长连接，
连接断了内核立刻知道——把心跳压到 3 s 是用应用层轮询重做传输层已经免费做的事，
几十台规模下每 3 秒一轮全网广播纯属浪费。P-5 已相应拆为 P-5（异常 ≤10 s）与
P-5b（优雅 ≤3 s），并注明各自的保证机制。新增集成测试 M3b（kill -9 后 ≤10 s 感知）。

### ⑨ 撤销即时性缺口 — **接受，这是评审第二大发现**

原文确实只写了「删公钥即撤销」，但已建立的 e2e 会话持有缓存对称密钥，会继续工作。
修法（MESH-DESIGN §2.1）：

1. 撤销 = MemberList 版本号 bump → 发现节点在 Subscribe 流上**推送**（这正是
   Subscribe 用推送不用轮询的原因）
2. 收到含撤销的高版本后，销毁该 deviceID 的活跃 e2e.Session 与路由表项
3. **分区对抗**：每条 e2e 帧携带它封存时的成员表版本；接收方发现版本落后于
   已知撤销即丢弃会话。被撤销方无法伪造更新版本——它已不能以成员身份签名

新增帧 `FrameMeshMembers`；R-1.3 与验收表已同步改写。

### ⑩ NodeID 长度歧义 — **部分接受**

「16 字节还是 16 个 hex 字符」的歧义指控不成立：两份文档均写明
`base32(sha256(pub))[:16]` 且 MESH-DESIGN §注释写有「16 字符 base32 有 80 bit 熵」。
但 MESH-DESIGN §2.1 说明段的简写 `sha256(pub)[:16]` 确实易被误读为字节切片——
评审举的「8 字节/16 hex」例子虽然是它自己的推演，暴露的读法风险是真的。
已把接口注释改为显式声明：**16 个 base32 字符（80 bit），非 16 字节、非 hex**，
并注明编码（base32 无填充、小写）——PR-M1 与 PR-M4 必须逐字节一致。

### ⑪ 加密算法描述不统一 — **不实，但建议被采纳**

核对结果：`grep -ci chacha` 在三份文档与图源中均为 **0**。
评审所称「MESH-DESIGN 同时提及 ChaCha20-Poly1305 / AES-256-GCM」不存在，
文档从头到尾只有 AES-256-GCM 一种。不存在「图文不一」。

但建议本身有价值：无 AES-NI 的低功耗 ARM 上两者性能差异大。
已在 `e2e.Session` 接口增加 `CipherSuite() byte`（0x01 AES-256-GCM 默认 /
0x02 ChaCha20-Poly1305），未知值拒绝握手而不是猜测——将来加新套件不用升版本号。

### ⑫ 阶段 1 `-L/-R` 如何挂载 — **接受，已补**

PR 计划确实没写。已补入 PR-M5：`e2e.Session.Streams()` 暴露为 `*mux.Session`，
`forward.Manager` 的 `Provider` 在组网模式下返回它——**阶段 1 的 forward 代码
零改动**，它只认 `Mux` 接口，不关心底下是直连 yamux 还是 e2e 内的 yamux。
于是 `cmesh forward -L 8080:nas:5432` 按设备名工作。

（更正评审一处小误：R-4.3/4.4 是「多路复用共存」与「按设备名寻址」，
SOCKS5 在后续阶段清单里，不在这两条。不影响结论。）

### ⑬ 512 KiB 与 32 KiB 混淆 — **接受，已补**

DESIGN.md 数据流章节已加说明：应用层 512 KiB 文件块是**断点续传的偏移单位**
（`.part` 的粒度）；传输层 32 KiB 记录是**加密与延迟下限的单位**。
一个 512 KiB 应用块经记录泵拆成 16 条 32 KiB 记录。前者管「断了从哪续」，
后者管「占用链路多久」。图上文件传输节点也已标注「512 KiB 应用块」。
