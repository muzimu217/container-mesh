## 1. 一句话架构

**四层：身份 → 发现 → 连接 → 路由。** 数据永远端到端加密，中转节点只转发密文。

```
┌─────────────────────────────────────────────────────────────┐
│ ④ 应用能力：消息 / 文件 / 端口转发 / 服务调用                 │
├─────────────────────────────────────────────────────────────┤
│ ③ 路由：直连优先，失败经其他成员中转（R-3.1、R-3.2）           │
├─────────────────────────────────────────────────────────────┤
│ ② 连接：打洞 / QUIC 直连 / 中转回退；一条连接多路复用          │
├─────────────────────────────────────────────────────────────┤
│ ① 发现：成员列表、地址、连通性（R-2.1、R-2.2）                 │
├─────────────────────────────────────────────────────────────┤
│ ⓪ 身份：长期密钥对、设备成员资格、撤销（R-1.1–R-1.5）          │
└─────────────────────────────────────────────────────────────┘
```

**与阶段 1 的根本差异**：阶段 1 是「A 和 B 通过中继配对」，中继是必需的中心。
组网里**没有中心**——每台都是对等节点，中继退化成「发现节点」（只发成员信息，不碰数据）
或「中转节点」（直连失败时借用，且不知道在转发谁的数据）。

## 2. 四层详解

### 2.1 ⓪ 身份层（服务 R-1.1–1.6）

**核心决定：一个密钥对就是一个身份，公钥即 ID。**

```
设备首次运行:
  cmesh init
    → 生成 Ed25519 密钥对
    → 私钥加密存储（口令派生密钥）
    → 公钥 = 设备身份 (deviceID = base32(sha256(pubkey))[:16])

加入一个网:
  cmesh join <invite>
    → invite 里含：网络 ID + 发现节点地址 + 网络公钥
    → 本设备用私钥签名一个加入请求
    → 已有成员批准（或用邀请码里的预共享授权）
    → 网络维护一份「成员公钥列表」
```

**为什么不用共享口令**（阶段 1 的做法）：

| | 共享口令 | 密钥对 |
|---|---|---|
| 撤销单台设备 | ❌ 换口令=全网重配 | ✅ 从成员列表删公钥 |
| 泄露影响 | 全网 | 单台 |
| 多设备 | 所有设备同一身份，无法区分 | 每台独立身份，同一账号下聚合 |
| 离线验证 | 需要口令 | 只需公钥 |

**「同一身份 ID、多设备共存」怎么实现**：
设备各自有密钥对，但**都属于同一个「账号」**（account key）。账号密钥签发的
「设备证书」把 deviceID 绑定到账号。所以：
- 数据面用 deviceID 认证（每台独立）
- 管理层用 accountID 聚合（`cmesh status` 显示「我的 4 台设备」）

```
account key (Ed25519, 离线保存或加密存本地)
    ├── signs → device cert A  (laptop)
    ├── signs → device cert B  (server-1)
    └── signs → device cert C  (k8s-pod)
```

**撤销**（R-1.3）：从成员列表移除该 deviceID。因为数据面认证用 deviceID，
移除后该设备既连不上别人，别人也不接受它的连接。**不需要换任何密钥。**

### 2.2 ① 发现层（服务 R-2.1–2.5）

**问题**：N 台机器怎么互相知道对方存在与地址？

**三种做法对比**：

| 做法 | 中心依赖 | 收敛速度 | 复杂度 | 适合 |
|---|---|---|---|---|
| 手工配置 IP 列表 | 无 | 人工 | 最低 | 3 台以内 |
| **发现节点（rendezvous）** | 弱：只发成员信息 | 秒级 | 中 | **本项目选这个** |
| DHT | 无 | 秒-分 | 高 | 数百台以上 |

**选择：发现节点，但它不是「中心」**（R-2.5）：

- 任何成员都可以兼任发现节点（`cmesh serve-discovery`）
- 客户端配置里可以列多个，故障切换
- **发现节点只转发成员信息（谁在线、地址、公钥），不转发用户数据**
- **发现节点以明文持有成员列表（仅内存），但它自己必须是成员。**
  它要验证签名、推送列表，必须能读。约束是「跑发现服务的机器必须是可信成员」；
  不接受就不部署——节点间手工交换一次地址也能组网（MESH-DESIGN §6.2）

```
节点 A 上线:
  A → 发现节点: 我是 deviceID=A，我的候选地址是 [1.2.3.4:5678, 内网IP:5678]
  发现节点 → A: 当前成员 = {B, C, D}，各自地址如下...
  发现节点 → B,C,D: 新成员 A 上线，地址如下...

之后 A↔B 直接打洞，不再经过发现节点。
```

**地址变化**（R-2.2）：每个节点定期向发现节点心跳（默认 30 s）。
发现节点检测到地址变化就广播给其他成员。**节点下线由心跳超时判定**（默认 90 s）。

### 2.3 ② 连接层（服务 R-3.1、R-3.4、R-4.3）

**复用阶段 1 的成果**：

| 能力 | 阶段 1 已实现 | 组网里怎么用 |
|---|---|---|
| STUN 候选发现 | `internal/p2p` | 直接复用 |
| UDP 打洞 | `internal/p2p` | 直接复用 |
| QUIC 直连 | `internal/p2pquic` | 直接复用，作为直连的数据面 |
| 记录泵 + yamux | `internal/peer` + `internal/mux` | 直接复用，多流复用 |
| SPAKE2 会话加密 | `internal/secure` | 保留作为**会话层**加密（见下） |

**两层加密**（这是组网必须的，阶段 1 没有）：

```
端到端层：deviceID_A ←→ deviceID_B   （中转节点看不到）
    ↑ 新增。SIGMA 模式：签名认证的 X25519 ECDH，身份密钥签名
    （SPAKE2 不适用——它的前提是共享口令，组网共享的是公钥）
会话层：一跳之内   （每一跳独立）
    ↑ 复用阶段 1 的 SPAKE2 或直接用 TLS 1.3（QUIC 自带）
```

**为什么必须两层**：中转节点 B 转发 A→C 的数据时，B 只能解开「A↔B」的会话层，
**解不开「A↔C」的端到端层**（R-3.5）。只有一层的话 B 就能读 A→C 的内容。

**连接建立顺序**（R-3.1 直连优先）：

```
1. 从发现层拿到对端候选地址
2. 尝试打洞（STUN + 同时开放）
3. 打洞成功 → QUIC 直连，建立会话层
4. 打洞失败 → 向发现节点要「能中转的成员列表」
5. 逐个尝试：A→B→C（B 是中转），建立 A↔B、B↔C 两段会话层
6. 端到端层在 A 与 C 之间直接协商（经 B 转发公钥）
```

**路径切换**（R-3.4）：直连断了先尝试重连直连（3 次），失败则退回中转；
直连恢复后自动切回。切换时**上层流不断**——这是阶段 1 踩过的坑
（记录泵中途换传输会丢半条记录），所以切换必须在**端到端层之下、会话层之上**做，
或者干脆重建连接让上层重试。

### 2.4 ③ 路由层（服务 R-3.2、R-3.3、R-3.6）

**问题**：A 要到 C，但直连不通，谁能中转？

**做法：距离向量 + 实测延迟，不做全局最优**。

```
每个节点维护:
  peers[deviceID] = {
    direct:   是否直连成功
    rtt:      实测往返延迟
    via:      如果非直连，经谁中转
    hops:     跳数
    updated:  最后更新时间
  }

选路规则（简单但够用）:
  1. 直连可用 → 用直连（永远优先，R-3.1）
  2. 否则选「rtt 最小且 hops 最少」的可用中转
  3. 中转节点自身负载超过配额 → 降级，选次优
```

**为什么不做全局最优**：全局最优需要全网状态同步（链路状态协议），
在几十台规模上收益不抵复杂度。距离向量 + 实测 RTT 已能覆盖 90% 场景。

**中转配额**（R-3.6、P-7）：每个节点默认允许中转 ≤ 50 MiB/s、≤ 20 条流。
超出后拒绝新的中转请求，但**不影响自身业务流量**。配额是防止「被当免费跳板」。

**环回防护**：距离向量协议必须有跳数上限（默认 8 跳）与 split-horizon
（不把从 B 学到的路由再告诉 B）。

## 3. 模块划分

### 3.1 包结构（规划）

```
cmd/cm
 └── internal/cli
      ├── internal/identity      【新】密钥、设备证书、账号聚合
      ├── internal/discovery     【新】成员列表、心跳、地址广播
      ├── internal/mesh          【新】路由表、选路、路径切换
      ├── internal/forward       【阶段1，冻结】端口转发
      ├── internal/peer          【阶段1，复用】会话 + 记录泵
      ├── internal/mux           【阶段1，复用】yamux 包装
      ├── internal/secure        【阶段1，复用】会话层加密
      ├── internal/relay         【阶段1，演化】→ 发现节点
      ├── internal/p2p           【阶段1，复用】打洞
      ├── internal/p2pquic       【阶段1，复用】QUIC 直连
      └── internal/wire          【扩展】新帧类型
```

### 3.2 新增包职责

| 包 | 职责 | 服务需求 | 预估行数 |
|---|---|---|---|
| `internal/identity` | Ed25519 密钥生成/存储/加载、设备证书签发与验证、账号聚合、撤销列表 | R-1.1–1.6 | ~450 |
| `internal/discovery` | 成员列表维护、心跳、地址变更广播、发现节点客户端与服务端 | R-2.1–2.5 | ~500 |
| `internal/mesh` | 路由表、距离向量、选路、路径切换、中转配额、环回防护 | R-3.1–3.6 | ~700 |
| `internal/e2e` | 端到端加密层（X25519 + AES-GCM），位于会话层之上 | R-3.5 | ~250 |

**总计约 2550 行新代码（含 CLI 约 350 行）+ 约 2260 行测试。**
分 5 个 PR（见 [`architecture/MESH-DESIGN.md`](architecture/MESH-DESIGN.md) §8）。

### 3.3 已有包的改动

| 包 | 改动 | 理由 |
|---|---|---|
| `internal/relay` | 从「两人配对」改为「成员列表广播」 | 现在是 `roles["A"]`/`roles["B"]` 硬编码（`relay.go:318`），要改成成员集合 |
| `internal/wire` | 新增身份/发现/路由帧类型 | 纯增量，不升版本号（C-4） |
| `internal/peer` | 会话层之上插入端到端层 | 记录泵不变 |
| `internal/cli` | 新增 `init` / `join` / `status` / `dial` / `serve-discovery` | |

### 3.4 冻结的包

`internal/forward`（端口转发）与 `internal/peer` 的文件传输逻辑**不改**，
组网直接复用它们作为「应用能力」。见 REQUIREMENTS §3.5。

## 4. 关键设计决策

### 4.1 身份（服务 R-1.x）

| 决策 | 选择 | 为什么 |
|---|---|---|
| 身份是什么 | Ed25519 密钥对，公钥即 ID | 可离线验证、可撤销、无中心 |
| 多设备怎么聚合 | 账号密钥签发设备证书 | 数据面按设备认证，管理层按账号聚合 |
| 私钥怎么存 | 加密文件（口令派生） | 不依赖系统密钥链（容器里没有） |
| 怎么进网 | 邀请（含网络公钥 + 发现节点地址） | 不能靠猜口令，否则等于没认证 |
| 怎么撤销 | 从成员列表删公钥 | 不换密钥，影响面最小 |

### 4.2 发现（服务 R-2.x）

| 决策 | 选择 | 为什么 |
|---|---|---|
| 拓扑信息来源 | 发现节点广播 | 秒级收敛，实现简单 |
| 发现节点是中心吗 | **不是**：任何成员可兼任，可配多个 | R-2.5：不要求固定某台 |
| 发现节点能看到什么 | 只有成员公钥与地址（加密传输） | 它不碰用户数据 |
| 下线判定 | 心跳超时 90 s | 兼顾收敛速度与误判 |
| 成员信息加密吗 | 是，用网络密钥 | 外部无法枚举网内设备（R-2.4） |

### 4.3 连接（服务 R-3.1、R-3.4）

| 决策 | 选择 | 为什么 |
|---|---|---|
| 默认路径 | 直连优先，**永远**优先 | R-3.1：直连延迟最低、不消耗他人带宽 |
| 直连失败 | 经其他成员中转 | R-3.2 |
| 加密层数 | **两层**：端到端 + 每跳会话 | R-3.5：中转节点不能读内容 |
| 路径切换 | 在端到端层之下做 | 阶段 1 的教训：记录泵中途换传输会丢半条记录 |
| 传输协议 | QUIC（直连）与 WebSocket（中转） | 复用阶段 1 已验证的路径 |

### 4.4 路由（服务 R-3.2、R-3.3、R-3.6）

| 决策 | 选择 | 为什么 |
|---|---|---|
| 路由算法 | 距离向量 + 实测 RTT | 几十台规模够用，全局最优不值复杂度 |
| 跳数上限 | 8 | 防环 |
| split-horizon | 是 | 防两节点互相指向 |
| 中转配额 | 50 MiB/s、20 流，默认开启 | 防止被当免费跳板（P-7） |
| 选路指标 | 先看直连，再看 RTT，再看跳数 | 简单可预测 |

### 4.5 复用阶段 1 的边界

**明确复用**：打洞、QUIC、记录泵、yamux、SPAKE2、文件传输、断点续传、端口转发。

**明确不复用**：
- 阶段 1 的「两人配对」模型（`roles["A"]/["B"]`）——这是要替换的核心
- 阶段 1 的「中继是必需中心」假设

## 5. 数据流

### 5.1 首次组网（服务 R-1.5、R-2.1）

```
设备 A（已有网络）              发现节点              新设备 B
     │                            │                     │
     │                            │            cmesh init（生成密钥）
     │                            │                     │
     │  生成邀请 ─────────────────>│                     │
     │  (网络ID + 发现地址 + 网络公钥)                     │
     │                            │                     │
     │                    邀请交给 B（扫码/复制/文件）      │
     │                            │<──── cmesh join ────│
     │                            │   (deviceID + 签名)  │
     │<─── 新成员待批准 ───────────│                     │
     │  批准 ─────────────────────>│                     │
     │                            │──── 成员列表 ───────>│
     │<────────── 成员列表 ────────│                     │
     │                            │                     │
     │<════════ 打洞 / 直连 ═══════════════════════════>│
```

### 5.2 三节点中转（服务 R-3.2、R-3.5）

```
A ──直连不通── C
A ──直连可用── B ──直连可用── C

建立路径:
  1. A 发现 C 不可直连
  2. A 查路由表：B 可以到 C，且 A↔B 直连
  3. A → B：请转发到 C
  4. B 检查配额 → 允许
  5. A↔C 协商端到端密钥（公钥经 B 转发）
  6. 数据路径：A ─[E2E密文]→ B ─[原样转发]→ C

B 看到什么:
  - 密文（解不开，因为没有 A↔C 的端到端密钥）
  - 元数据：谁在什么时候转发了多少字节（这是不可避免的）
B 看不到:
  - 明文内容
  - A 与 C 协商出的密钥
```

### 5.3 路径切换（服务 R-3.4）

```
直连正常:  A ══直连══> C

直连断开:
  1. 检测（QUIC 空闲超时 / 心跳失败）
  2. 尝试重连直连 3 次（指数退避，最多 5 s）
  3. 失败 → 查路由表找中转
  4. 建立 A→B→C
  5. 上层流：端到端层重新协商，应用层感知为「短暂卡顿」

直连恢复:
  1. 发现层报告 C 的新地址可直连
  2. 建立新直连
  3. 切回（旧中转路径保留 30 s 作为备份）
```

## 6. 部署拓扑

### 6.1 最小可用（3 台）

```
   笔记本（家里 NAT 后）        云服务器（公网 IP）         K8s Pod（受限）
        │                            │                        │
        └──── 打洞或经云服务器中转 ───┴────────────────────────┘
                                      ↑
                          兼任「发现节点」（可选）
```

**任何一台有可达端口的机器都能兼任发现节点。** 没有它也能工作——
只要节点之间能通过某种方式交换到地址（比如手工配置一次，之后靠已有连接传播）。

### 6.2 无公网节点（全部在 NAT 后）

```
   A（家）  B（公司）  C（另一处）
      \       |       /
       \      |      /
        发现节点（第三方的、或其中一台有端口映射的）
```

**这种情况下必须有至少一个可达点**，否则任何 P2P 系统都无法建立首次连接。
这是网络的基本限制，不是设计缺陷。

### 6.3 与阶段 1 部署的关系

阶段 1 的部署（一台中继 + N 个客户端）在组网里仍然有效：
那台中继可以继续当**发现节点**，客户端升级后自动获得组网能力。
**已有部署不需要推倒重来。**

## 7. 演进路线

| 阶段 | 内容 | 状态 |
|---|---|---|
| **1** | 端口转发 + 多路复用 + 记录泵 | ✅ 已合并 main，**冻结** |
| **2** | 组网：身份 + 发现 + 直连 + 中转路由 | 设计中 |
| **3** | 界面：拓扑可视化、设备列表、延迟/带宽 | 规划 |
| **4** | 智能选路：按实测带宽优化路径 | 规划 |

**阶段 2 内部拆分**（按可独立验收的顺序）：

| 子阶段 | 内容 | 验收 |
|---|---|---|
| 2a | 身份层：`init` / `join` / `status`（无网络） | 两个身份文件能互相验证 |
| 2b | 发现层：成员列表、心跳、收敛 | 3 节点 10 s 内互相看见 |
| 2c | 直连：打洞接入组网 | 任意两台 `cmesh dial` 直连 |
| 2d | 中转路由：距离向量、配额 | 阻断直连后仍可通 |
| 2e | 端到端加密层 | 中转节点抓包看不到明文 |
