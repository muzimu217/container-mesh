### 1.2 数据面分层（关键设计）

**这是整个项目最重要的一个决定**：mux 必须在加密层**之上**，不能在下面。

```
┌──────────────────────────────────────────────────────────┐
│  应用：SSH / psql / curl / 文件传输                        │
├──────────────────────────────────────────────────────────┤
│  业务流：forward 转发流（kind=1） │ 控制流（kind=0）        │  ← yamux 多路复用
├──────────────────────────────────────────────────────────┤
│  internal/mux：yamux 包装（流数信号量、CloseWrite）         │
├──────────────────────────────────────────────────────────┤
│  internal/peer.Pump：记录泵（32 KiB 一条，单读单写）         │  ← 顺序收敛点
├──────────────────────────────────────────────────────────┤
│  internal/secure：SPAKE2 + HKDF + AES-256-GCM（严格递增）   │
├──────────────────────────────────────────────────────────┤
│  internal/wsconn / p2pquic / p2p2：传输                     │
├──────────────────────────────────────────────────────────┤
│  WebSocket（中继） 或 QUIC/UDP（P2P 直连）                  │
└──────────────────────────────────────────────────────────┘
```

**为什么不能反过来**（服务 R-2.1、R-2.4）：

`secure.Session` 是「每方向一个严格递增计数器」的 AEAD 通道，要求帧**严格按发送顺序**到达。
而 yamux 的 `recvLoop` 在应用读取之前就按 streamID 把帧分发到各流缓冲区，跨流到达顺序在那一刻就丢了。
若多个 goroutine 各自解密，它们会看到乱序的全局计数器，**解密必然失败**。

记录泵把「多流并发」重新收敛成「单序列」，`secure.go` 一行不改。

### 1.3 三种接入模式（服务 R-2.1、R-5.1、R-5.2）

| 模式 | 前提 | 用户怎么用 | 阶段 |
|---|---|---|---|
| **2a 端口转发** | 无 | `cmesh forward -L 8080:db:5432` | ✅ 已实现 |
| **2a SOCKS5** | 无 | `cmesh proxy --socks5 :1080` + 客户端配代理 | 规划 |
| **2b L3 虚拟网络** | 有 TUN + `CAP_NET_ADMIN` | `cmesh up` 后 `ping`/`ssh` 透明 | 规划 |

**共同点**：都不需要改对端应用。区别只在「应用怎么知道要走隧道」。

## 2. 模块划分

### 2.1 包依赖（无环）

```
cmd/cm
 └── internal/cli            参数解析 + 生命周期 + 输出
      ├── internal/forward    转发策略 + 监听器 + 管道
      │     ├── internal/mux  yamux 包装（只依赖 yamux + stdlib）
      │     └── internal/wire 线格式（纯编解码）
      ├── internal/peer       会话 + 记录泵 + 帧分发
      │     ├── internal/secure   PAKE + AEAD
      │     └── internal/wire
      ├── internal/relay      中继服务
      ├── internal/probe      能力探测
      └── internal/wsconn / p2pquic / p2p / p2p2   传输
```

**约束**：`internal/mux` 不导入 `wire`/`peer`/`secure`。它只认识「一条有序字节流」和「一个字节的 stream kind」，
所以 yamux 的 v0.x API 变动被完全隔离在这一个包里。

## 3. 关键设计决策

每条都标注服务的需求与理由。完整的决策历史见 [`decisions.md`](decisions.md)。

### 3.1 安全边界（服务 R-3.1–3.8）

| 决策 | 选择 | 为什么 |
|---|---|---|
| 口令如何交给中继 | 房间号 = `HMAC-SHA256(code)` | 中继拿不到 code，无法离线枚举弱口令（R-3.2） |
| 如何发现主动中继 | 两端显示 SAS，可 `--expect-sas` 强制 | RoomID 只挡被动监听；SAS 是唯一能发现 MITM 的手段（R-3.3） |
| 转发的默认值 | 拒绝一切，零值即拒绝 | 忘记配置不能等于开放代理（R-3.4） |
| 策略与拨号顺序 | **先策略后拨号** | 反了的话被拒绝的请求仍产生出站连接，等于端口扫描器（R-3.6） |
| `-R` 的授权 | 独立的 `--accept-reverse` + `--allow-listen-port` | `-R` 让对端在本机开端口，风险量级不同于 `-L`（R-3.5） |
| `-R` 的目标来源 | preamble 只带监听器 ID，ID 查本地配置 | 结构性保证：对端无法让我们拨它指定的地址 |

### 3.2 传输层（服务 R-1.1–1.9、P-1）

| 决策 | 选择 | 为什么 |
|---|---|---|
| 记录大小 | **32 KiB**，一条记录一次 transport 写 | 512 KiB 记录在 2 MiB/s 链路上是 250 ms 队头阻塞；32 KiB 降到 15.6 ms（见下） |
| 写侧批量合并 | **不做** | 合并后加密单元回到 512 KiB，队头阻塞原样回来，且只在链路忙时触发 |
| 帧版本 | 保持 1，靠 `caps` 协商 | 升版本会让新旧二进制的 `send`/`recv` 立刻不兼容（C-4） |
| 多路复用库 | yamux v0.1.2 | smux v1 会静默丢数据；QUIC 原生多流吞吐低一个数量级 |
| 传输切换 | 单流允许；mux 建连后锁定 | 切换会丢弃在途半条记录，AEAD 必然失败（实测丢 25/49 字节） |
| P2P | 默认关闭，失败回退中继 | 回环实测直连比中继慢 16 倍（13 vs 256 MiB/s） |

**记录大小的推理链**（这是被评审推翻过一次的决策，值得完整保留）：

```
最初：512 KiB（回环 539.3 MiB/s，比 64 KiB 的 211.9 快 2.5 倍）
  ↓ 评审指出：那两个数字都是回环测的，真实链路 2–12 MiB/s
问题：记录泵必须收齐整条记录才能解密，所以一条记录占链路多久 = 其他流的延迟下限
     512 KiB / 2 MiB/s = 250 ms  ← 一边 scp 一边敲 SSH 会明显卡顿
  ↓ 改为 32 KiB
结果：延迟下限 15.6 ms，AEAD 实测仍有 1408 MB/s（不是瓶颈）
  ↓ 想用「16 条合并成一次写」补回 syscall
发现：合并后接收端要收齐 512 KiB 才能解密任何一条 —— 队头阻塞原样回来
结论：不做合并。实测 512 MiB 回环 515/615/594 MiB/s，syscall 不是瓶颈
```

### 3.3 可观测性（服务 R-4.1–4.3）

| 决策 | 选择 | 为什么 |
|---|---|---|
| 会话数怎么算 | 独立计数器（splice 处增减） | `len(rooms)` 在配对瞬间就删了，**有流量的那一刻恰好是 0** |
| 状态点含义 | 「中继响应了」，不是「有流量」 | 空闲中继是健康的；按会话数变色会让正常服务器看起来挂了 |
| 看板形态 | 内嵌单页，无外部请求 | 中继是单二进制分发；有外部请求的监控页在「没人看得到你流量」的工具里是泄漏 |
| 暴露什么 | 只有聚合计数 | 房间号是 code 的派生值，公开它等于给出可离线攻击的校验值 |

### 3.4 CLI 输出（服务 O-4）

| 决策 | 选择 | 为什么 |
|---|---|---|
| 结构化日志级别 | 默认 Warning 以上 | 之前 `slog.Default()` 的 Info 会盖过命令自己的输出 |
| 用户可见事件 | 走 `Handler.OnStatus`，不走日志级别 | 续传提示曾被日志级别吞掉，e2e 当场抓住 |
| 启动横幅 | 无条件打印 | 过滤后启动成功却零输出，看起来像失败 |
| 错误 | `cmesh: <一句话>`，退出码非零 | 之前 `main` 只取退出码不打印消息，参数错误全是静默退出 |

## 4. 数据流

### 4.1 `-L` 转发（服务 R-2.1、R-2.4、R-3.6）

```
应用            节点 A（-L 侧）                     节点 B（--accept 侧）      目标
 │                    │                                    │                    │
 ├─ TCP connect ─────>│                                    │                    │
 │                    │ ① 检查 pending 上限                 │                    │
 │                    │ ② OpenStream(kind=1) ──────────────>│                    │
 │                    │                                    │ ③ 检查 --accept     │
 │                    │ ④ Preamble{kind=direct, "db:5432"} >│                    │
 │                    │                                    │ ⑤ 令牌桶            │
 │                    │                                    │ ⑥ 白名单（返回 IP）  │
 │                    │                                    │ ⑦ 拨号（只用该 IP）──>│
 │                    │<────────────── Status(OK) ──────────│                    │
 │<═══════════════════ 双向字节流 + 半关闭传播 ═════════════════════════════════>│
```

**四道闸的顺序是安全属性**：③ 在最前（连 preamble 都不读），⑤⑥ 在 ⑦ 之前。
反过来就等于给了对端一个端口扫描器，答案藏在状态码和响应时间里。

### 4.2 `-R` 转发（服务 R-2.2、R-3.5）

```
应用         节点 B（hoster）                节点 A（requester）         本地目标
 │                │                                │                      │
 ├─ connect ─────>│ ① --accept-reverse?            │                      │
 │                │ ② --allow-listen-port?         │                      │
 │                │ ③ loopback 或 --listen-all?    │                      │
 │                │ ④ bind 成功 ────────────────────│                      │
 │                │                                │                      │
 │                │ ⑤ OpenStream(kind=1) ─────────>│                      │
 │                │ ⑥ Preamble{kind=reverse, ID} ─>│                      │
 │                │                                │ ⑦ 按 ID 查本地配置    │
 │                │                                │ ⑧ 拨本地 target ─────>│
 │                │<──────────── Status(OK) ───────│                      │
 │<═══════════════ 双向字节流 ═════════════════════════════════════════════>│
```

**注意方向容易想反**：bind 端口的是 hoster，但**开回连流、拨最终目标的也是 hoster**；
requester 只做「查 ID → 拨本地配置的 target」。所以 requester 需要 `--accept-reverse`（服务回连流），
但**不需要** `--allow-listen-port`（它不 bind）。

### 4.3 记录泵的读/写循环（服务 R-2.3）

```
读侧（唯一调用 OpenFrame 的 goroutine）:
   transport.Recv() ──> secure.OpenFrame() ──> FrameStreamData? ──> readQ.Put()
                          ↑                                          （有界阻塞）
                    遇到 ErrTransportSwitched:
                    mux 模式下 → 判死（切换会丢半条记录）
                    单流模式   → continue（帧边界清晰，最多丢一帧）

写侧（唯一调用 SealFrame 的 goroutine）:
   writeQ.Get() ──> secure.SealFrame() ──> transport.Send()
    （有界阻塞）        一条记录一次写（不合并）
```

**核心不变量**：`OpenFrame` 永远只有一个 goroutine 调用，`SealFrame` 永远只有一个。
这是 `secure` 的严格递增计数器能工作的前提，也是 mux 不能放在加密层之下的根本原因。

## 5. 部署拓扑

### 5.1 最小可用（服务 O-2、O-3）

```
     你的笔记本                    一台有公网 IP 的机器               受限容器
   （零入站端口）                    （1 个入站 TCP 端口）          （零入站端口）
        │                                  │                          │
        └────── 出站 WS ──────────────────>│<────── 出站 WS ──────────┘
                                      cmesh relay
```

**唯一需要入站端口的角色是中继。** 客户端全部零入站。

### 5.2 复用已有 80/443（安全组改不了时）

```
   客户端 ──wss://域名/cmesh/──> nginx ──proxy_pass──> relay 127.0.0.1:8082
```

⚠️ **必须加在现有 `server { }` 块里作为 `location`**，不能新建 server 块——
同一个 `server_name` 的第二个 server 块会遮蔽原有站点（踩过一次，把生产站搞挂）。

### 5.3 什么样的机器能当中继（唯一判据）

**别的机器能不能主动连到它。** 资源几乎不相关（实测 8.5 MB 空载 / 13.5 MB 带连接）。

| 机器 | 能当？ | 说明 |
|---|---|---|
| 有公网 IP 的云服务器 | ✅ | 放行一个端口，或复用 80/443 |
| 反代后面的机器 | ✅ | nginx 转发 `/ws` |
| 只能出站的托管容器 | ❌ | 无公网入站端口（实测 Cloud Studio：所有候选路径 500 或 IDE 壳） |
| 家庭宽带 / NAT 后 | ❌ | 除非有端口映射或公网 IPv6 |

## 6. 演进路线

| 阶段 | 内容 | 状态 | 决策门 |
|---|---|---|---|
| **1** | 端口转发（`-L`/`-R`）+ mux + 记录泵 | ✅ 已合并 main | 吞吐 ≥ 485 MiB/s、e2e 全绿、`-race` 全绿 |
| **2a** | SOCKS5 代理（任意 TCP/UDP，不预设端口） | 规划 | 库层吞吐 ≥ 200 MiB/s |
| **2b** | L3 虚拟网络（需 TUN） | 规划 | MTU 必须 ≤ 1200，否则 TCP 卡死 |
| **3** | 中继互联（真正的网格） | 研究完成，不实现 | — |
| **4** | 智能选路（按 RTT 排序） | 规划 | — |

**阶段 3 为什么不实现**：链式转发需要在节点间建隧道并处理环路、分层加密、故障切换，
复杂度相当于再实现一层网络协议。而实测单跳跨云已有 11–12 MiB/s，多跳只会更慢（每跳都要解密再加密）。
当前「客户端持有中继列表 + 故障切换」已覆盖 90% 的可用性需求。
