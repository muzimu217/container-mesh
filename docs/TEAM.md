# 专家团（Virtual Expert Panel）

> 本项目由一个执行者实现，但**决策由多个视角做出**。本文定义的专家是虚拟角色：
> 每个角色对应一组**入口问题**（开工前必须回答）、**否决权**（可阻止合并）、
> 与**自有产物**（唯一维护责任人）。执行者轮换扮演，但纪律是：
> **每个 PR 必须通过全部六个角色的门**，协调者在每轮结束时出报告。
>
> 为什么不直接列「职责」：职责会被跳过，门不会——门关着，代码就进不了 main。

**版本**：T1（2026-10-24）
**上一轮报告**：见 [`ROUND-LOG.md`](ROUND-LOG.md)

## 1. 角色与门

### ① 首席协调（Lead）

**不是最厉害的，是唯一对「本轮结束」负责的。**

| 项 | 内容 |
|---|---|
| 入口问题 | 本轮做哪个 PR？为什么是它而不是别的？前置依赖满足了吗？ |
| 否决权 | 范围蔓延：PR 塞进了计划外的东西，整轮打回 |
| 自有产物 | [`ROUND-LOG.md`](ROUND-LOG.md)、里程碑排期、跨角色冲突裁决 |
| 每轮产出 | **Round 报告**（格式见 §3），没有报告不算结束 |

### ② 需求专家（Product）

| 项 | 内容 |
|---|---|
| 入口问题 | 这个改动对应哪个 `R-*` 编号？没有编号的不做。验收标准可判定吗（能写成测试断言）？ |
| 否决权 | ① 改动无需求编号；② 验收标准不可判定；③ 「代码这么写了所以需求就是这样」 |
| 自有产物 | [`REQUIREMENTS.md`](REQUIREMENTS.md)（R-* / N-* / P-* / C-* / O-* 编号） |
| 纪律 | 需求与实现冲突时，**先改本文档再改代码**（T-0.2） |

### ③ 开发专家（Implementation）

| 项 | 内容 |
|---|---|
| 入口问题 | 包依赖还无环吗？新抽象解决的是哪个具体问题（答不出 = 删）？注释写的是约束还是叙事（叙事 = 删）？ |
| 否决权 | ① 引入环依赖；② 「将来可能需要」的抽象层；③ 被推翻的方案没留一句为什么 |
| 自有产物 | [`DESIGN.md`](DESIGN.md)、包结构、`go vet` / `gofmt` 干净 |
| 纪律 | `internal/mux` 不导入项目内其他包这类边界一旦破了，整轮打回 |

### ④ 测试专家（QA）

| 项 | 内容 |
|---|---|
| 入口问题 | **新守门测试改坏过代码并看到红了吗？**（没验证过会红的不算测试，T-2.1）性能断言用的是绝对阈值还是退化量级？（绝对阈值 = 打回，T-2.4） |
| 否决权 | ① 守门测试没做过红绿验证；② 用 `net.Pipe` 测半关闭这类「测了错误分支」的设置；③ 时序测试没在 `-race` 下跑过 |
| 自有产物 | [`tests/run-tests.sh`](../tests/run-tests.sh)、混沌测试、测试稳定性（连续 10 轮 `-race` 不偶发） |
| 已有教训 | 窗口测试曾**空转**：破坏窗口门它依然绿，因为 pacing 才是实际约束。空转的测试比没有测试更危险 |

### ⑤ 安全专家（Security）

| 项 | 内容 |
|---|---|
| 入口问题 | 新输入按攻击者构造校验了吗（长度/编码/控制字符/范围）？默认值是零值拒绝吗？策略检查在副作用**之前**吗？ |
| 否决权 | ① 忘记配置 ≠ 拒绝（零值必须拒绝）；② 拨号/bind/写盘先于策略检查；③ 日志或可观测端点泄漏房间号、code、对端地址 |
| 自有产物 | 威胁模型（MESH-DESIGN §5）、[`CONVENTIONS.md`](CONVENTIONS.md) T-4.x |
| 红线 | 中继/中转节点**永远**不能读到明文；密钥文件绝不入 git |

### ⑥ 性能专家（Performance）

| 项 | 内容 |
|---|---|
| 入口问题 | 这个改动影响哪条 `P-*` 门槛？回退判定用 A/B 同刻对照了吗？（拿历史最好值当基线 = 打回，T-2.6）新开销记进 X 风险表了吗？ |
| 否决权 | ① 未经实测的性能结论（标 `[推断]` 的不能当验收）；② A/B 不在同一时刻跑 |
| 自有产物 | P-1~P-7 门槛、X 风险表（MESH-DESIGN §9）、基准方法 |
| 已有教训 | 「批量合并省 syscall」被实测否决（加密单元回到 512 KiB）；A/B 不同刻会把环境噪声误判成回退 |

## 2. 迭代仪式（每个 PR 走一遍）

```
协调者宣布本轮 PR 与对应 R-* 编号
        │
   ②需求 ──→ 编号存在？验收可判定？          ─┐
   ③开发 ──→ 依赖无环？抽象有据？            ─┤
   ④测试 ──→ 守门测试红绿验证过？            ─┼─ 全过才可推
   ⑤安全 ──→ 零值拒绝？先策略后副作用？       ─┤   （T-1.1 本地全绿）
   ⑥性能 ──→ P 门槛不回退？                  ─┘
        │
   CI 绿 → PR → 合并
        │
   ①协调者写 Round 报告 → ROUND-LOG.md
```

**关键规则**：

- 角色的门**在提交前**过，不是提交后补（T-1.6：一次性做对）
- 任何角色行使否决权时，**必须写下原因**——否决理由沉淀进 CONVENTIONS 的事故表
- 一个人扮演多角色时，门依然分开过：提交信息里每个角色的关键答复要能对上

## 3. Round 报告格式

协调者每轮必须产出，写入 [`ROUND-LOG.md`](ROUND-LOG.md)：

```markdown
## Round N — <PR 名>（<日期>）

**交付**：一句话 + 提交号
**对应需求**：R-x.y, R-x.z

| 角色 | 结论 | 关键发现/否决 |
|---|---|---|
| ②需求 | ✅/⚠️ | … |
| ③开发 | ✅/⚠️ | … |
| ④测试 | ✅/⚠️ | 红绿验证：破坏了什么、看到了什么红 |
| ⑤安全 | ✅/⚠️ | … |
| ⑥性能 | ✅/⚠️ | 实测数字 / A/B 对照 |

**遗留**：转入下一轮或技术债清单的项
**下一轮**：PR-M?，理由
```

## 5. 为什么是这六个

不是拍脑袋。每个角色对应本项目**已经付出过代价**的一类事故（见 CONVENTIONS §7）：

| 角色 | 对应的真实事故 |
|---|---|
| ④测试 | 吞吐测试在 main 上 1/6 概率红；窗口测试空转；`net.Pipe` 测错分支 |
| ⑤安全 | XFF 伪造绕过限流；握手 panic；`volume prune` 删生产卷 |
| ⑥性能 | 512 KiB 记录的队头阻塞推理错误；批量合并被实测否决 |
| ②需求 | R1 把产品定义成「传输工具」，实际是组网——返工了整套文档 |
| ③开发 | mux 三文件的锁归属模糊，合并回一个文件 |
| ①协调 | 阶段 1 与组网混在一个提交里，评审阻力翻倍 |

**没有对应事故的角色不设。** 等出现「因为没人管 X 而付代价」的事故，再增列。
