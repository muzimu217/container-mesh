# 统一凭证的完整接线设计（M4 (a) 最后一环）

日期：2026-11-13。状态：**设计已定，凭证包与委派签发已实现并有测试；本文件描述尚未接线的部分。**
需求：R-6.7。已落地：`internal/credential`、`identity.Delegation`、`DeviceCert.SignerPub`。

## 0. 为什么要分两步

一键入网看起来只是「少一个审批动作」，但它要跨过一条信任边界：**发现节点必须能
接纳一张它没有签过的证书**。当前信任模型是：成员证书由账号私钥签发，任何成员
都能用账号公钥验签（MESH-DESIGN §5.1）；发现节点自己**不持有账号私钥**，所以它
无法伪造成员。

如果为了「一键」把账号私钥塞进凭证，凭证持有者就成了账号的永久签发权威——
凭证一泄漏，整个账号的信任边界就没了。所以凭证里放的是**委派签发密钥**，而委派
签发出来的证书**不是账号证书**：它必须在信任核里走一条新的、窄的路。

## 1. 角色与钥匙

| 角色 | 持有什么 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 账号持有者 | 账号私钥 | 签发成员证书、签发委派记录 | —— |
| 凭证持有者（团队成员） | 凭证私密半（委派私钥） | 在额度与有效期内为自己签发设备证书 | 不能签发账号证书、不能改额度、不能让已入册设备被除名 |
| 发现节点 | 账号**公钥**、成员名册 | 验证凭证签名、验证委派签名的证书、按额度准入 | 不能伪造成员（没有账号私钥，也没有委派私钥） |

关键点：**委派私钥永远不进入发现节点**。节点只看到委派公钥，因此它只能「承认」
委派签过的东西，不能「制造」任何东西。

## 2. 数据流

```
① 账号持有者：  cmesh cred create --disc <锚点> --ttl 24h --max-devices 10
                → 打印一行凭证（公开半：账号签名；私密半：委派私钥）

② 成员设备：    cmesh join --cred <那行>
                a. 解码凭证，取委派私钥
                b. 用委派私钥为自己的设备公钥签一张证书（SignerPub = 委派公钥）
                c. 把「凭证公开半 + 设备证书」POST 到锚点 /mesh/enroll

③ 发现节点：    a. 用账号公钥验凭证签名（账号公钥来自 --account-pub）
                b. 检查凭证有效期、额度（已委派签发的成员数 < max_devices）
                c. 用委派公钥验设备证书；证书的 AccountID 必须等于凭证的 AccountID
                d. 把委派记录（**就是凭证的公开半本身**）与证书一起写进名册，
                   先落盘再推送

④ 所有成员：    快照里同时带着委派记录，因此能验证委派签名的成员证书
                （否则这张证书会被当成伪造的丢掉——见 §4 的坑）
```

**关键实现决定（实测踩出来的）**：委派记录与凭证的公开半是**同一个结构、同一份签名**。
最初把它们做成两种形状，锚点无法为「名册记录」补一份账号签名（它没有账号私钥），
于是委派记录到了成员那边验不过 → 被当伪造丢掉 → **设备已经入册，却对所有人（包括
它自己）不可见，加入方空等 60 秒**。合并成同一结构后，入网耗时从 60s 降到 0s。

## 3. 额度与撤销语义（必须先定清，否则上线后必然扯皮）

- **额度**：按**委派公钥**计数（一个委派 = 一把签发密钥 = 一个额度桶）。计数来源
  是名册里 `cert.SignerPub == 委派公钥` 的成员数，因此**撤销成员会归还额度**，
  节点重启后计数也自动恢复（不依赖内存计数）。
- **额度不因节点重启丢失**：这是「计数来自名册」而不是「内存计数器」的理由。
- **撤销委派本身**（让整把签发密钥失效）：把委派记录从名册里移除即可——新的注册
  请求会因为「找不到该委派记录」被拒。**已入册的设备不受影响**（它们是名册里的
  成员，撤销委派不等于撤销成员）。要撤销单个设备，仍走现有的 `account device-remove`。
- **凭证过期**：过期后新的注册被拒；已入册设备**继续有效**直到证书自己过期。
  凭证的 TTL 是「签发窗口」，不是「成员寿命」。
- **证书 TTL ≤ 凭证 TTL**：否则会出现「凭证过期了但证书还活着」的窗口，成员数量
  不受额度约束地续命。

## 4. 三个必须一起改的坑（缺一个就是静默故障）

1. **快照必须带委派记录**。客户端 `verifySnapshot` 会逐个用**账号公钥**验成员证书；
   委派签名的证书验不过 → 会被**当作伪造成员丢掉** → 新设备入网了却对所有人
   不可见（连它自己都看不到自己）。所以 `MemberSnapshot` 必须携带委派列表，
   客户端在遇到 `SignerPub != nil` 的证书时，去找匹配的委派记录、验委派的账号
   签名、再用委派公钥验证书。
2. **名册必须能存委派记录**。`identity.MemberList` 增加 delegations 段；`Add`
   之外需要 `AddDelegation` / `RemoveDelegation` / `DelegationFor(pub)`。
3. **发现节点必须能持久化**。名册文件归 CLI 管（`serve-discovery` 热加载
   members.json）。节点在内存里加成员，下一次热加载会把它冲掉——所以 enroll
   必须走「先写文件、再热加载」的路径，或由 CLI 提供一个持久化回调给节点。
   **没有持久化回调的节点必须拒绝准入**（宁可拒绝入网，也不能出现「准入后下一
   次热加载就消失」的成员）。

## 5. 与既有约束的相容性

- **共享出口限流**：注册请求与配对 /ws 共用按出口的预算。一键入网会让多台设备同时
  敲门，因此 enroll 端点要**单独计数并给更紧的预算**（否则一次「团队上线」能把
  整个出口的配额打满，正是第 34 轮 429 饱和的成因）。
- **R-2.4（非成员不可枚举）**：enroll 端点不接受任何查询参数式的「试探」，凭证
  签名不过就是不过，不透露「这个账号存在吗」。
- **C-4 协议向后兼容**：`DeviceCert.SignerPub` 是 `omitempty`，旧证书的签名字节
  不变；旧节点收到新证书会验不过 → 拒（这是预期的：旧节点不懂委派，宁可严格）。

## 6. 验收标准（下一轮实现的完成判据）

| 项 | 判据 |
|---|---|
| 一条命令入网 | 成员设备 `cmesh join --cred <串>` 后 ≤5s 可被对端 ping 通，无需任何人工审批 |
| 额度生效 | 额度 2 的凭证，第 3 台设备注册被拒，错误文案说明「额度已用尽」而非「签名无效」 |
| 过期生效 | 过期凭证注册被拒，文案说明「凭证已于 X 过期」 |
| 撤销委派 | 移除委派记录后，同一凭证的新注册被拒；已入册成员不受影响 |
| 可见性 | 新设备出现在**所有**成员的成员视图里（包括未持凭证的旧成员） |
| 持久化 | enroll 后重启节点，成员仍在名册（不因热加载消失） |
| 旧成员不受影响 | 全部账号直签证书的既有成员，其视图与行为零变化（线兼容） |
| 限流隔离 | 一次团队级入网不把该出口的配对 /ws 预算打空（两种请求分别计数） |

## 7. 不做（明确划界）

- **不做 ACL / 多身份**：仍是一个身份 = 一个团队（U2 边界，N-8）。
- **不做自动续期**：凭证过期就重新签发。
- **不把账号私钥放进任何可交付的字符串**：这是本设计的红线。
- **不承诺「跨网通用凭证」**：一机多网（M5）时，每张网一张凭证。
