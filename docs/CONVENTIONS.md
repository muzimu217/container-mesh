# 开发范式与条约（Conventions）

> 这份文件是**约束**，不是建议。每条都对应一次真实事故或一次评审打回。
> 与本文件冲突的做法一律视为错误，即使它能跑通。

**版本**：V1（2026-10-23）

---

## 0. 三层文档纪律

**顺序不可颠倒：需求 → 设计 → 技术。**

```
REQUIREMENTS.md   要解决谁的什么问题、什么算成功
      ↓
DESIGN.md         用什么结构满足
      ↓
architecture/     具体怎么做、为什么这么做
research/         支撑决策的实测数据
decisions.md      每条决策的历史（含被推翻的）
```

### 条约

| 编号 | 条约 |
|---|---|
| **T-0.1** | 新增功能前，先在 `REQUIREMENTS.md` 有编号。没有需求编号的功能不做。 |
| **T-0.2** | 改实现前先看 `DESIGN.md` 对应章节。设计与实现不一致时，**先改文档**。 |
| **T-0.3** | 需求编号一旦分配**永不复用**。废弃的需求保留并标注原因。 |
| **T-0.4** | 技术决策写进 `decisions.md`，带 `D<n>` 编号、理由、以及**被推翻时为什么**。 |
| **T-0.5** | 任何「实测」结论必须能复现：给命令、给环境、给数字。推断要标 `[推断]`。 |

**反例**：`STAGE1-PORTFORWARD.md` 曾写「记录大小 512 KiB」，理由是两个回环吞吐数字。
这两个数字是真的，但**推理错了**——真实链路是 2–12 MiB/s，回环数字不适用。
教训：`[实测]` 标签只对被测环境成立，跨环境外推必须重新测（见 T-0.5）。

## 1. 提交纪律

### 1.1 提交前必须本地跑完整 CI 路线

| 编号 | 条约 |
|---|---|
| **T-1.1** | 任何 push / 开 PR 之前，本地把 CI 会跑的检查**全部跑一遍并通过**。不允许把验证推给 CI 或维护者。 |
| **T-1.2** | 先查 base 本身是否绿。base 红的时候不叠加 PR——别人的红会让你无辜变红。 |
| **T-1.3** | 本地全绿 = 可以推；有任何红 = 不推。不许「先推上去看 CI」。 |

**本地 CI 路线**（与 `.github/workflows/ci.yml` 一致）：

```bash
gofmt -l .                      # 必须无输出
go vet ./...
go build ./...
go test ./... -race -count=1
bash tests/run-tests.sh --quick
GOOS=linux GOARCH=amd64 go build ./cmd/cm
GOOS=linux GOARCH=arm64 go build ./cmd/cm
```

### 1.2 已推送的 PR 不随意改动

| 编号 | 条约 |
|---|---|
| **T-1.4** | 已 push 的分支默认不再 force-push。rebase / amend / 拆分提交都会产生 review 噪点、重置 review 状态。 |
| **T-1.5** | 仅三种情况允许改动：① 维护者明确要求 ② CI 失败且根因在我方 ③ 发现严重内容错误（夹带无关删除、DCO 缺失、身份错误）。 |
| **T-1.6** | **提交前一次性做对**：身份、DCO、文件分区、内容纯净度、提交拆分——全部在首次 push 前验完。 |

### 1.3 提交拆分

| 编号 | 条约 |
|---|---|
| **T-1.7** | 一个 PR 只做一件事。跨两个交互模型的改动必须拆开（例：`-L` 与 `-R` 分开）。 |
| **T-1.8** | 大改动按逻辑拆 2–3 个 commit：`fix(scope):` / `test(scope):` / `docs(scope):`。 |
| **T-1.9** | 纯清理（删死代码、改格式）单独一个 PR，不与功能混在一起。 |

**反例**：`-R` 的实现曾与 `-L` 混在一个提交里，导致评审要同时理解两套拓扑。
拆开后每个 PR 都能独立验收。

### 1.4 Git 外发操作需口头放行

| 编号 | 条约 |
|---|---|
| **T-1.10** | `commit / push / merge / rebase / cherry-pick / revert / reset / tag`，以及 `gh pr / gh release / gh repo(写)`，执行前必须在对话里说明意图，**等明确放行**。 |
| **T-1.11** | 放行只对当次说明的具体操作有效，不外推。不得改写命令形式绕开语义。 |
| **T-1.12** | 只读操作（`status` / `log` / `diff` / `show` / `fetch`）不受限。 |

## 2. 测试纪律

### 2.1 测试必须能证明「改坏了会红」

| 编号 | 条约 |
|---|---|
| **T-2.1** | 新增守门测试后，**故意把代码改坏，确认测试变红**，再改回来。没验证过会红的测试不算测试。 |
| **T-2.2** | 修 bug 必须先写出能复现该 bug 的测试（红），再修（绿）。 |
| **T-2.3** | 断言要断言**行为**，不要断言实现细节。断言日志字符串时必须确认那行日志属于用户可见契约。 |

**反例**：断点续传的 e2e 断言 `grep "resuming transfer.*from=400000"`。
我把日志级别从 Info 提到 Warn 后，这行消失了，测试变红——**测试是对的**，
问题在实现：续传是用户可见行为，不该被日志级别吞掉。改成走 `OnStatus` 回调。

### 2.2 性能测试不能用绝对阈值

| 编号 | 条约 |
|---|---|
| **T-2.4** | 性能断言不能用「墙钟时间 / 大小」的绝对阈值。`go test ./...` 并行跑包时，CPU 争抢能让健康链路掉到 4 MiB/s。 |
| **T-2.5** | 断言「是否发生了数量级退化」：用**用时**判断是否撞上重传停顿（秒级），而不是用吞吐判断。 |
| **T-2.6** | 性能回归判定必须 **A/B 同刻对照**。拿「历史最好值」当基线会把环境噪声误判成代码问题。 |
| **T-2.7** | 依赖时序的仿真测试（如拥塞控制）在 `-race` 下跳过——race 检测器会扰动时序。 |

**反例**：`internal/p2p` 的吞吐测试断言 `mbps < 5` 就失败。在 8 核机器上并行跑时实测 3.9–4.0 MiB/s，
**在未修改的 main 上约 1/6 概率变红**，阻塞了无关的合并。
改为断言「用时 > 2 秒」（重传停顿的量级），健康传输是毫秒级，两者差 180 倍。

### 2.3 测试环境必须真实

| 编号 | 条约 |
|---|---|
| **T-2.8** | 测半关闭必须用真实 TCP（`*net.TCPConn`），不能用 `net.Pipe`——它不实现 `CloseWrite`，会走错分支。 |
| **T-2.9** | 涉及并发泄漏的测试必须断言 goroutine 回落基线，不能只看「没崩」。 |
| **T-2.10** | 端到端验证必须用**真实进程 + 真实服务**，不能只有单元测试。至少一次手动跑通完整链路。 |

**反例**：`net.Pipe` 写的半关闭测试是绿的，但它测的是「整连接关闭」降级路径。
生产路径（`*net.TCPConn`、yamux 流）支持半关闭，两者行为完全不同。改用真实 TCP 后才真正验证。

## 3. 代码纪律

### 3.1 注释写约束，不写叙事

| 编号 | 条约 |
|---|---|
| **T-3.1** | 注释只写**代码本身无法表达的约束**：「为什么必须是这个值」「为什么不能换顺序」。 |
| **T-3.2** | 禁止写「这个函数做了什么」（看代码就知道）、「下一行做什么」、「这个改动为什么正确」（那是给 reviewer 的）。 |
| **T-3.3** | 被推翻的方案要留一句为什么被推翻——否则下一个人会重新提出它。 |

**正例**（`pump.go`）：

```go
// 32 KiB, not 512 KiB. The 512 KiB figure came from loopback throughput and is
// the wrong optimisation target here: a large record is a latency floor for
// every other stream sharing the connection.
RecordSize int
```

**反例**：

```go
// Set the record size.
p.cfg.RecordSize = 32 << 10
```

### 3.2 安全属性必须是结构性的

| 编号 | 条约 |
|---|---|
| **T-3.4** | 安全默认值必须**零值即拒绝**，不能靠「记得配」。 |
| **T-3.5** | 策略检查必须在副作用（拨号、bind、写盘）**之前**。顺序是安全属性。 |
| **T-3.6** | 不可信输入（对端发来的任何字节）一律按攻击者构造来校验：长度、编码、控制字符、范围。 |
| **T-3.7** | 返回「要用的具体值」而不是 bool。返回 bool 会逼调用方重新解析，那是 TOCTOU。 |

**正例**：`AllowList.Permits` 返回**要拨的具体 IP**，而不是 `bool`。
返回 bool 的话调用方得再解析一次主机名，DNS 就有机会在检查与连接之间改变。

### 3.3 依赖与抽象

| 编号 | 条约 |
|---|---|
| **T-3.8** | 新增依赖必须说明它买到了什么。能四十行手写清楚的不引库（例：令牌桶）。 |
| **T-3.9** | 抽象层必须解决一个具体问题。为「将来可能需要」而加的抽象一律删掉。 |
| **T-3.10** | 包依赖必须无环。`internal/mux` 只依赖 yamux + stdlib，不导入项目内其他包。 |

**反例**：`internal/mux` 原本设计成 `config.go` / `mux.go` / `stream.go` 三个文件（410 行）。
实现时发现三者的锁都落在同一组字段上，拆开只让归属模糊。合并成一个文件 382 行。

### 3.4 错误处理

| 编号 | 条约 |
|---|---|
| **T-3.11** | 错误必须让用户知道该做什么。「连接失败」不合格，「peer refused target (status: denied, reason: port 5432 not in --allow-port)」合格。 |
| **T-3.12** | 策略拒绝与故障必须可区分（`Denied` vs `DialFail`）——前者改配置，后者修服务。 |
| **T-3.13** | 不得吞掉错误。至少记一行日志；关键路径（写盘、校验）必须显式检查。 |

## 4. 安全纪律

| 编号 | 条约 |
|---|---|
| **T-4.1** | 中继永远不能看到明文或口令。任何让它能看到的设计直接否决。 |
| **T-4.2** | 日志不得记录 code、完整房间号、对端地址。房间号只以脱敏形式出现（`redactRoom`）。 |
| **T-4.3** | 可观测性端点只暴露聚合计数。房间号是 code 的派生值，公开它等于给出可离线攻击的校验值。 |
| **T-4.4** | 生产环境的密钥、`.env`、数据库 dump **绝不入库**。加入 `.gitignore` 并说明原因。 |
| **T-4.5** | 不在生产服务器上执行 `volume prune`、`rm -rf` 这类不可逆操作。已发生过一次数据丢失。 |
| **T-4.6** | 改生产 nginx 配置只能加 `location`，**不能新建同 `server_name` 的 server 块**——会遮蔽原站点。改前备份、改后 `nginx -t` + 验证生产站点 200。 |

## 5. 文档纪律

| 编号 | 条约 |
|---|---|
| **T-5.1** | 文档与代码不一致时，**文档错**——先改文档。不允许代码改完文档不动。 |
| **T-5.2** | 实现推翻了设计时，在设计文档里写清「原方案是什么、为什么被推翻」，不要直接删。 |
| **T-5.3** | 数字必须标注来源：`[实测]` / `[查证]` / `[推断]`。推断值不得当验收标准。 |
| **T-5.4** | 未做的事如实写「未做」，不要用「检查后没问题」掩盖。 |
| **T-5.5** | 每份文档开头写明它在三层中的位置和它回答什么问题。 |

## 6. 每轮迭代的检查清单

提交前逐条打勾：

```
□ 需求有编号吗？（REQUIREMENTS.md）
□ 设计与需求一致吗？（DESIGN.md）
□ 决策记录了吗？（decisions.md，含被推翻的方案）
□ gofmt / vet / build 干净？
□ go test ./... -race 全绿？
□ 连续 10 轮 -race 不偶发失败？（改了并发或时序时必查）
□ e2e 全过？
□ 新测试能证明「改坏了会红」吗？
□ 性能没回退？（A/B 同刻对照）
□ 注释写的是约束，不是叙事？
□ 安全默认值是零值拒绝吗？
□ 策略检查在副作用之前吗？
□ 文档同步了吗？
□ 提交拆分合理吗？（一个 PR 一件事）
□ 有口头放行吗？
```

## 7. 事故记录（为什么有这些条约）

| 事故 | 教训 | 对应条约 |
|---|---|---|
| `podman volume prune` 删掉两个生产卷，内容不可恢复 | 生产主机上永不 prune | T-4.5 |
| 新建 `server_name` 相同的 nginx server 块，遮蔽生产站点 | 只加 location | T-4.6 |
| 吞吐测试在未修改的 main 上 1/6 概率红，阻塞无关合并 | 性能断言不用绝对阈值 | T-2.4–2.7 |
| 断点续传提示被日志级别吞掉 | 用户可见事件不走日志级别 | T-2.3、T-3.11 |
| `net.Pipe` 测半关闭测的是错误分支 | 测试环境必须真实 | T-2.8 |
| 记录大小 512 KiB 的推理基于回环数字 | 跨环境外推必须重测 | T-0.5 |
| 评估 Cloud Studio 时说「会休眠所以不能当中继」，实际 9.4 天没睡 | 先量再下结论 | T-0.5 |
| `-R` 与 `-L` 混在一个提交里 | 一个 PR 一件事 | T-1.7 |
| `main` 对 `ExitError` 只取退出码不打印消息 | 错误必须让用户知道该做什么 | T-3.11 |
