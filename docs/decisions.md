# 技术选型：两台 NAT 后低权限容器之间的互通

> 版本信息核对时间：2026-10-17。croc v11.5.4、Syncthing v2.1.6、iroh v1.3.0、pion/webrtc v4.2.24。

## 0. 约束（来自主代理实测，直接采信）

| 事实 | 影响 |
|---|---|
| 容器 root，`CapEff=a00c05fb` | 无 `CAP_NET_ADMIN`(12)、`CAP_NET_RAW`(13)、`CAP_SYS_ADMIN`(21)、`CAP_MKNOD`(27) |
| `/dev/net/tun` 不存在 | **TUN 完全不可用**，任何基于 TUN 的组网方案出局 |
| TCP + UDP 出站均可用，无入站 | 只能做「主动外连 + 中继/打洞」 |
| croc 在容器内可用，公共 relay 可达 | 证明「出站 TCP/WebSocket 到公共 relay」这条路走得通 |
| EasyTier `--no-tun` 在容器内异常（连 127.0.0.1 都 2 秒超时，本地 macOS 正常） | **不基于 EasyTier 设计**；这个现象本身也是重要线索，见 §5.2 |
| 上海出口经透明代理，`github.com → 198.18.0.5`，TCP 握手 0.1ms | 典型 fake-IP 代理特征，见 §5.1 |
| Cloudflare Tunnel 100MB 限制只作用于 HTTP 请求体 | WebSocket 流式传输不受限，本项目采用 WS 是对的 |

## 1. 四个方案的真实工作量与可行性

先说结论：**推荐 croc 作为近期可用方案，本项目自研的 WebSocket 中继方案作为可控替代**。不推荐 iroh（Go 侧不可用）、不推荐 pion 自建（工作量与运维成本远超收益）、不推荐 Syncthing（面向目录同步而非一次性传输，内存与协议开销不划算）。

### 1.1 pion/webrtc 自建

**要自己写的东西**：信令服务（WebSocket 服务器 + 房间管理）、ICE 服务器配置、TURN 服务器（coturn）部署与运维、DataChannel 上的分块协议、断点续传状态机、背压控制、文件元数据交换。

- 小消息：DataChannel 直接给消息语义，工作量中等。
- 大文件：**必须自己实现分块 + 流控**。DataChannel 有 `bufferedAmount` 但需要自己做窗口，否则内存爆掉。断点续传也要自己设计（记录 offset、校验 prefix）。
- 打洞：依赖 ICE，能力等价于浏览器 WebRTC。
- TURN 运维：coturn 需要公网 IP、开放 3478/udp+tcp 与中继端口段（默认 49152-65535），还要处理证书、认证、配额。

**真实工作量估计**：可用原型 3-5 人日；能上生产（TURN 高可用、监控、限速、NAT 类型诊断）3-6 人周。

**关键问题：两台都在 NAT 后时打洞成功率？**
公开数据（Chrome UMA 统计口径）大致是：直连成功 75-80%，20-25% 需要 relay。分 NAT 类型看，full-cone ≈98%、address-restricted ≈90%、port-restricted ≈75%、**symmetric ≈20%**。两个都在 symmetric NAT 后（企业网、部分移动网络、以及本例这种「透明代理出口」）基本必然走 relay。

**判断**：这个容器环境是「透明代理出口 + 上海机房」，不是典型家宽。代理层往往会破坏 UDP 打洞（fake-IP 场景下 STUN 返回的映射地址可能根本不可用），实际成功率应该按**偏差情形**估计，即大概率走 relay。所以「自建 WebRTC」的真实形态是「自建 TURN」，那不如直接用一个简单的 WS 中继。

**TURN 传 GB 文件的带宽成本**：
- Twilio：US/EU $0.40/GB，亚太 $0.60/GB，悉尼/圣保罗 $0.80/GB。
- 注意计费口径：TURN 按**双向**计费，中继 1GB 文件实际计费约 2GB。所以 100GB 文件走亚太 TURN ≈ 200GB × $0.60 = **$120**。
- 自建 coturn：Hetzner 约 €5-15/月含 20TB 流量；阿里云/腾讯云按流量约 ¥0.5-0.8/GB，100GB 双向 ≈ ¥100-160。

### 1.2 iroh（QUIC + 内建 relay + 打洞）

**优点**：设计最现代。QUIC + TLS1.3，按公钥拨号，QNT（QUIC-NAT-Traversal）把打洞做成 QUIC 层操作，relay 是无状态的（转发加密包，不维护会话），运维成本理论上最低。官方称打洞成功率约 90%，95% 的数据量走直连。

**致命问题（对本项目）**：**Go 绑定不可用于生产**。
- 官方 `iroh-ffi` 提供 Python/Swift/Kotlin/Node.js 绑定，Go 明确标注 "Community maintained"。
- Go 绑定是 `git.coopcloud.tech/decentral1se/iroh-go`，需要 cgo + 预编译 Rust 动态库 + `LD_LIBRARY_PATH`，支持矩阵只有 **Linux x86_64/aarch64 (musl)**，且是社区维护的 FFI 包装。
- 本项目要交付「真实可运行且本地验证」的代码，本机是 macOS arm64，Go 绑定在这里跑不起来。用 Rust 重写则与现有工具链（Go 1.27 已就绪，Rust 未安装）冲突。

**判断**：iroh 在架构上是最优解，但**当前 Go 生态落地成本过高**。如果将来团队愿意用 Rust 或 Python，iroh 值得重估。注意其「90% 打洞成功」是项目自述，独立分析也提醒应视为文档声明而非基准测试结果。

**relay 成本**：iroh relay 无状态，带宽仍是主要成本，量级与 TURN 相同（数据必须过 relay）。自建 `iroh-relay` 的成本 ≈ 一台 VPS + 出网流量。

### 1.3 croc（已验证可用）

**优点**：
- 容器内**实测可用**（主代理已验证，能拿到 transfer code，公共 relay 可达）。
- 断点续传、目录传输、PAKE 加密、压缩，全部现成。
- 中继是纯 TCP，`croc relay` 一条命令自建，端口 9009-9013。

**关键认知纠正**：croc 的 WAN 模式**不做 UDP 打洞**，它就是「双方各自出站连 relay，relay 把两条 TCP 连接 staple 起来」。所以：
- 打洞成功率这个问题对 croc **不适用**——它 100% 走 relay（除非同 LAN，此时用本地 relay 走直连）。
- 换句话说，croc 的可靠性等于「relay 可达性」，这在本环境里已经被验证。
- 代价是**所有流量都过 relay**，没有直连优化。传 GB 文件时 relay 带宽就是成本。

**relay 带宽成本**：作者自述公共 relay 2023 年每月 20TB 流量、$40-50/月（早期 $5/月）。这个数字说明：单条 relay 的带宽成本并不高，但如果自建且流量大，按云厂商流量计费仍然可观。自建 `croc relay` 在 Hetzner 这类含大流量的 VPS 上最划算。

**工作量**：几乎为零（已有二进制）。缺点是它是「文件传输工具」，不是「双向消息通道」——`croc send` 传文本也算，但要做长连接双向聊天、自定义协议，就得嵌它的库或者干脆自己写。

### 1.4 Syncthing（用户态、P2P+中继、断点、增量）

**优点**：用户态、无 TUN、断点续传、块级增量、加密、成熟。

**缺点（针对本任务）**：
1. **它是目录同步，不是一次性传输**。要传一个文件得建共享文件夹、配对设备 ID、等扫描。语义不匹配。
2. **协议重**：Block Exchange Protocol，需要索引、块哈希数据库。单条协议消息上限 500MB（间接限制单文件约 1.25GB，实际现代版本已改善但仍有历史包袱）。
3. **内存与 CPU**：社区反馈 relay 每会话约 4MB 缓冲，1000 会话需 4GB；客户端本身也不轻。低权限容器里跑常驻同步守护进程不划算。
4. **中继带宽**：社区 relay 普遍 <10Mbit，实测中继传输约 540MB/min vs 直连 928MB/min。自建 `strelaysrv` 可以解决速度，但**默认会加入公共 relay pool 帮别人转发流量**，必须显式 `-pools=""` 才是私有。
5. 打洞依赖 UPnP/NAT-PMP + 中继，成功率与 WebRTC 同量级。

**判断**：除非需求变成「两台机器持续镜像某个目录」，否则 Syncthing 是过度设计。

## 2. 直接回答两个关键问题

### Q1: 两台都在 NAT 后时，打洞成功率有多高？

| 场景 | 估计成功率 | 依据 |
|---|---|---|
| 双方家宽 port-restricted cone | 75-90% | 公开 NAT 类型统计 |
| 双方 symmetric NAT | ~20% | 同上 |
| 企业网/代理出口 | 20-50% | 防火墙策略不可控 |
| **本例（上海 + 透明代理）** | **大概率失败，按走 relay 设计** | 代理层改写/劫持 UDP，fake-IP 使 STUN 映射不可信 |

结论：**不要把打洞当作前提**。任何方案都必须有 relay 兜底，并且要能「先用 relay 建立，再尝试升级到直连」（iroh/Tailscale 的做法），而不是「先打洞，失败再降级」。

### Q2: 回落 TURN 后传 GB 文件的带宽成本是多少？

以 100GB 文件、亚太区为例：

| 方式 | 计费口径 | 估算成本 |
|---|---|---|
| Twilio TURN 亚太 | $0.60/GB × 双向 200GB | **~$120** |
| Cloudflare TURN | $0.05/GB × 200GB | ~$10 |
| 自建 coturn @ Hetzner | 含 20TB 流量 | **~€5-15/月**（100GB 无额外费用） |
| 自建 coturn @ 云厂商按流量 | ¥0.5-0.8/GB × 200GB | ~¥100-160 |
| croc 公共 relay | 免费（作者自担） | $0，但不可依赖 |
| 本项目 WS 中继 @ 同 VPS | 同 coturn | 同 coturn |

**关键结论**：TURN/relay 的成本差异不在协议，而在**你从谁那里买带宽**。自建 VPS 比云 TURN 便宜 1-2 个数量级。所以真正的决策是「是否愿意运维一台中继 VPS」，而不是「选哪个协议」。

另一个容易被忽略的点：**TURN 按双向计费**。很多成本估算只算单向，实际会翻倍。

## 3. 最终推荐

### 推荐：croc 用于「尽快能传文件」，本项目自研 `cmesh` 用于「可控的双向通道」

理由：

1. **croc 已经在本环境实测可用**，这是唯一被验证过的事实。如果目标只是「把文件从 A 传到 B」，直接用 croc，零开发。
2. 但 croc 不满足「小消息双向收发 + 长连接 + 自定义协议」的需求。本项目的 `cmesh` 用**与 croc 完全相同的网络形态**（双方出站 WebSocket → 中继 staple），因此继承了 croc 已验证的可行性，同时提供：
   - 双向消息通道（长连接）
   - 可自建 relay（一条命令）
   - 显式断点续传（`.part` + offset 协商）
   - 端到端加密（SPAKE2 + AES-256-GCM），relay 无法解密
3. **不选 iroh**：Go 绑定不可用于生产，本机无法验证，违背「真实跑通」的交付要求。
4. **不选 pion 自建**：本质是自建 TURN，工作量最大而收益与 WS 中继相同（本环境打洞大概率失败）。
5. **不选 Syncthing**：语义不匹配，常驻进程开销大。

### 演进路径（如果将来要优化）

1. 当前：WS 中继，全流量过 relay。
2. 加直连：在 relay 建立后，双方交换 STUN 得到的映射地址，尝试 UDP 打洞；成功则用 QUIC 或加密 UDP 替换数据面，relay 只做信令。这就是 iroh/Tailscale 的形态，但可以用 Go 自己实现（pion/ice 或手写）。
3. 如果团队接受 Rust：直接换 iroh，省掉上述全部工作。

## 4. 本项目的协议选择理由

| 决策 | 选择 | 理由 |
|---|---|---|
| 传输层 | WebSocket over TCP/TLS | 穿透 HTTP 代理与 CDN；无 100MB 请求体限制；天然消息分帧；croc 已验证同形态可行 |
| 加密 | SPAKE2 (pake/v3) + HKDF + AES-256-GCM | PAKE 抵抗离线字典攻击；短码即可安全；每方向独立密钥 + 单调计数器防重放 |
| 分块 | 64 KiB/frame | 远低于 1 MiB 帧上限，代理友好，续传粒度细 |
| 续传 | `.part` 文件 + offset 协商 + 全文件 SHA-256 | 简单、可验证；坏前缀最多浪费一次重传 |
| 中继 | 无状态转发（不解析内容） | relay 无法读流量；水平扩展只需加实例 |

## 5. 两个值得记录的异常现象

### 5.1 透明代理与 fake-IP

`github.com → 198.18.0.5` 属于 `198.18.0.0/15`（RFC 2544 基准测试网段），是 Clash/Surge 一类代理的 fake-IP 池。特征：
- TCP 握手 0.1ms（本地代理直接应答，不是真实 RTT）
- DNS 解析返回代理伪造地址

影响：
- **STUN 结果不可信**：UDP 可能被代理接管，返回的映射地址未必真实可达。
- **打洞几乎不可能成功**：代理通常不转发任意 UDP。
- **TCP/WS 中继不受影响**：代理对 TCP 是正常转发的，这正是 croc 和本项目能工作的原因。

### 5.2 EasyTier `--no-tun` 异常

现象：能监听端口，但连接 127.0.0.1 和 1.1.1.1:443 全部 2 秒超时；同样参数在 macOS 正常。

未查明原因（本任务未做进一步排查），但可以给出几个假设：
1. `--no-tun` 模式下仍尝试创建某种 socket 或设置 sockopt，被 seccomp 拦截后进入异常状态。
2. 容器内缺少某些 `/proc` 或 `/sys` 条目，导致其网络栈初始化半途失败。
3. 透明代理对非标准端口的 UDP/TCP 处理异常，而 EasyTier 的心跳恰好命中。

**这也说明一个方法论**：在这个容器里，「能监听端口」不等于「能出站连接」，权限探测必须实测出站，不能只看 bind 成功。本项目的 `probe` 模块正是按这个原则设计的。

# 2026-10-18 第二轮：自动化组网能力（心跳 / 重连 / 多 relay / 双向传输）

目标：从「能传一次」升级为「常驻节点」——relay 或网络抖动后自动恢复、
多 relay 容灾、会话中随时双向传文件。以下为本轮的关键决定与被否决的方案。

## D8. 心跳放在 WS 传输层，而不是应用层 FramePing

**决定**：`wsconn` 对每条连接做 20s ping / 60s 读超时（pong 与数据都会刷新
deadline）；`FramePing/FramePong` 保留但不再主动使用。

**为什么不用应用层心跳**：
1. 发送方流式传文件时**只写不读**（SendFile 循环里没有 Recv），应用层 ping
   到达对端后没人应答，反而会被 relay 误判为死连接——会话读泵（见 D9）必须
   常驻读取，WS 层 pong 由 gorilla 在读循环内自动回复，天然解决这个问题。
2. relay 侧对每条腿也需要独立的存活判定，splice 只转发字节不解析协议，
   应用层心跳帮不了它。

**实现要点（都踩过坑）**：
- 读 deadline 在每次 `Recv` 进入时刷新 + pong handler 到达时刷新。不能只在
  handler 里刷新：无流量时读阻塞在 `ReadMessage` 上，pong 不来就没有刷新时机。
- **`Close()` 绝不能碰 `readMu`**：阻塞在 `ReadMessage` 上的读泵永远持有
  readMu，Close 若先取 closeMu 再取 readMu 就是必然死锁（e2e 实测抓到，
  见 `TestCloseUnblocksRecv` 回归测试）。stopLive 通道由 closeMu 保护。
- 一次只有一个 WS 帧在路上，单帧传输时间超过 60s（即持续速率 <10 KB/s）
  会被误杀——已知下限，README 已标注。

## D9. peer.Session 改为单一读泵 + 按帧类型分发

**决定**：会话内只有读泵一个 goroutine 读传输层；`FrameMsg` 走回调，
`FrameFileChunk/Done` 送入当前 `InboundTransfer`，`FrameFileAccept/Reject/Result`
送入 outbound 通道给 `SendFile` 等待者，`FramePing` 自动回 pong。

**为什么必须改**：旧 API 是 pull 式（调用方各自 `recvFrame`）。常驻模式下
读循环 + 用户 `/file` 命令 + 发送方等待 result 三者会并发调用 Recv——两个
goroutine 抢同一条连接是竞态，靠运气不崩。分发模型让两个传输方向完全独立：
发送方只写 chunk、从专属通道收 accept/result；接收方从专属通道收 chunk。
这也是「双向同时传一个文件」能成立的前提（`TestDuplexTransfers`）。

**API 取舍**：放弃 pull 式 `ReceiveFile/RecvFrame`，改为 `Handler.OnOffer`
回调（返回 bool 表示是否接管传输）。测试同步迁移。

## D10. 断线重连 = 客户端拨号循环 + relay「后来者踢占位」

**决定**：客户端 `Node.Run` 常驻循环——按 relay 列表顺序轮拨、指数退避、
每次重连完整重跑 SPAKE2（无会话状态可恢复，代码即身份）；relay 侧同房间
同角色的新连接**直接踢掉旧泊位**（last-writer-wins），配对中的僵尸连接
不阻塞重连。

**否决的方案**：relay 主动探测泊位连接是否存活。
1. 读探测：配对前客户端就可能发出 PAKE msg1（TCP 缓冲，splice 启动后转发），
   这是协议的合法行为——监测器要么把数据当违规杀连接（实测打挂全部转发
   测试），要么把偷读的数据缓冲回放（需要包装整个连接类型）。
2. deadline 循环读：gorilla 的读错误是 sticky 的，deadline 在帧边界超时一次
   就永久污染连接，不能用于轮询。
3. MSG_PEEK 原始 fd 探测：可行但要按平台分叉（unix/其他），复杂度不值。

踢占位方案零探测、零平台分叉：能重新出示 code 的新连接理应比僵尸优先
（code 本来就是唯一凭据）。代价是知道 code 的攻击者可以踢掉等待中的对方，
但知道 code 本身就能完成握手，攻击面没有扩大。

## D11. 文件分块 64 KiB → 512 KiB

每帧的固定开销（AEAD、WS 帧头、splice 两次拷贝）在真实广域网上是吞吐主导项。
回环实测 512 MiB：211.9 → 539.3 MiB/s（2.5×）。1 MiB 线上限内仍有余量，
但更大会放大慢链路上的队头阻塞（见 D8 的 10 KB/s 下限）。续传粒度从 64 KiB
变粗到 512 KiB，对 GB 级文件无关紧要。

## D12. 多 relay：有序列表 + 配对窗口轮换

**决定**：`--relay A,B,C` 按固定顺序尝试；连接失败或 `--pair-window`（默认
60s，一次性命令压到 10s）内对方未出现就换下一台；整轮失败退避后重试。

**收敛性论证**：两端用同一份列表，各自独立选「第一台活的」。分歧只发生在
健康状态视差（一端认为 A 活、另一端认为 A 死）——此时两端先后都会轮到 B
并配对，代价是一次 pair-window 的等待。部署上建议国内/海外各一台、两端
按自己区域优先排序列表（详见 deploy/README.md 的路由策略）。

**否决**：按 RTT 选最快 relay——两端可能选到不同的 relay 永不相遇，需要
中央协调或把 relay 编进 code，复杂度不成比例。

## D13. 一次性命令的有界性

常驻模式（`--stay`）一切重试无上限（守护语义）；一次性命令（`--stay=false`）
必须能自己退出：
- `MaxConnectAttempts=8`：拨号尝试上限；
- `MaxTransferAttempts=3`：offer 重试上限（配合 D14 的 offer 超时）；
- code 格式错误（如长度 <6）归类为 `ErrProtocol` **永久错误**，立即退出而非
  重试（实测发现短 code 会导致无限重试）。

## D14. SendFile 的两个等待点加超时

等 accept 30s（"没人收"变成错误而不是永恒等待），等 result 10min（此时
数据已在途，超时只防连接假死）。没有这两个超时，单端测试里发送方会永久
挂在 outboundCh 上。

## D15. probe STUN 扩为多服务器并行（含国内）

默认列表：`stun.miwifi.com`、`stun.qq.com`（国内）+ `stun.cloudflare.com`、
`stun.l.google.com`（海外），并行查询、逐个报告。实测（中国移动网络）：
miwifi 138ms 成功、qq 超时、Cloudflare/Google 可达但返回**不同的端口映射**
（24628/50063/58112）——单服务器探测会低估 NAT 限制，多服务器的分歧本身
就是诊断信息。报告新增 `network.stun[]` 结构化字段。

## D16. 部署形态

`Dockerfile`（多阶段、distroless、非 root）+ `deploy/`（compose + Caddy
自动 HTTPS + 免费资源矩阵：Oracle Always Free / Cloudflare Tunnel / Workers
DO / 国内轻量新用户）。免费选项的真实约束是**流量配额**（relay 转发量 ≈
文件大小 ×2），不是 CPU/内存。公网部署未实测，诚实标注在 deploy/README.md。

# 2026-10-19 第三轮：外部评审报告驱动的安全加固

依据外部评审（`container-mesh-review-2026-10-18.md`）逐条验证并修复。以下记录
每条决定的技术取舍，特别是**没有完全照搬报告建议**的地方。

## D17. room 改为 HMAC 派生 —— 但纯 HMAC 不足以防 MITM

**报告建议**：`room = HMAC(code, salt)`，让 relay 看不到 code。

**采纳，但补充了关键一点**：单纯改 room 只解决「relay 直接拿到 code」，
**并不阻止主动 MITM**——因为 relay 拿到 `RoomID(code)` 后仍可对弱 code 做
**离线字典攻击**（room 是 code 的确定性函数，等于一个 verifier）。一旦猜出
code，MITM 依然成立。

**因此同时引入 SAS**：
- `secure.RoomID(code)`：`HMAC-SHA256(normalize(code), "container-mesh/room/v1")`
  前 16 字节 hex。relay 只看到不可逆标签。
- `secure.Session.ShortAuth()`：6 位十进制，由 session key 经**独立 HKDF 标签
  `v1 SAS`** 派生。两端必须算出相同值。
- 连接建立时打印 `SAS=xxxxxx fingerprint=...`，由双方带外比对。

**踩到的坑**：最初用 `sendAEAD` 的密钥派生 SAS，导致两端数值不同——因为
A→B 与 B→A 是**不同方向**的密钥。必须从 session key 单独派生一个**对称**
的 SAS key。

**未做的**：没有实现自动 SAS 校验。自动校验需要预共享身份（证书/公钥），
那会把问题转移成另一套密钥分发。当前设计明确要求人工比对一次。

## D18. relay 限流：按 IP 而非按 room

**报告建议**：按源 IP/房间做令牌桶。

**采纳按 IP，拒绝按 room**：按 room 限流会误伤——同一 code 的两个合法端
本来就会各开一个连接，且重连会再开；按 room 限流需要区分「合法重连」与
「恶意 squatting」，而这两者在 relay 视角完全一样（都是同 room+role 的新连接）。
按 IP 限流则没有这个歧义，且能同时挡住「大量建房耗尽 MaxRooms」。

- 并发连接上限：默认 16/IP
- 新建速率：默认 120/分钟/IP（令牌桶，按秒补充）
- `X-Forwarded-For` / `X-Real-IP` 参与判定：生产部署几乎一定在 nginx/Caddy 后面，
  否则所有客户端共享代理的预算
- 空闲状态定期 sweep，避免 map 无限增长

**保留「后来者踢占位」**：它是断线重连能工作的前提（见 D10）。限流降低了
被滥用的成本，但没有消除——知道 code 的人仍可踢掉等待者。这是可用性问题，
不是机密性问题，且 SAS 会让真正的 MITM 暴露。

## D19. 接收端：上限 + 空间预检 + 不覆盖

**报告建议**：加 `--max-file-size` + `statfs` 检查 + 名字白名单。

**全部采纳**，几处实现细节：

- **默认 16 GiB，而非报告建议的 4 GiB**：本项目的目标场景包含大文件传输
  （README 里 1 GiB 是常规用例），4 GiB 会误伤。上限的意义是「防写满磁盘」，
  不是「限制合法用途」；真正的护栏是空间预检。
- **用 `Bavail` 而非 `Bfree`**：`Bfree` 包含 root 保留块，非 root 接收端会
  在预检通过后仍然写失败——而目标场景恰恰是非 root 容器。
- **名字白名单放宽到包含 `()[]@#`**：第一版只允许 `[A-Za-z0-9._+- ]`，测试
  立刻打脸——`My File (1).zip` 是极常见的下载文件名。这些都是安全的
  （不是路径分隔符、不是 shell 元字符）。
- **不覆盖用 link-then-remove**：`os.Rename` 会静默覆盖，等于让对端能销毁
  无关文件。`os.Link` 在目标存在时返回 EEXIST，天然是「不存在才创建」；
  不支持硬链接的文件系统（FAT/部分网络盘）回退为显式存在性检查。

**顺带修掉的真实 bug**：`publishNoClobber` 失败时原本直接 `return nil, err`，
**没有给发送方回 FileResult**，发送方会一直等到 10 分钟超时。测试
（`TestRefusesToOverwriteExistingFile`）以 40 秒超时暴露了它。现在发布失败
也会回一个 `OK:false` 的结果。

## D20. 删除 insecure TLS 选项（而非保留）

**报告建议**：删除或显式审计。

**选择删除**：`wsconn.DialOptions.InsecureSkipVerify` 没有任何 CLI 调用点，
属于「将来可能被误接上」的死代码。保留一个能静默关闭证书校验的开关，在
一个以「relay 不可信」为前提的项目里是自相矛盾的——TLS 校验保护的是
「relay 是不是真的 relay」，关掉它等于放弃唯一的路由层身份检查。
需要自签证书的场景应该用私有 CA，而不是跳过校验。

## D21. module 路径对齐仓库

`github.com/blackevil/container-mesh` → `github.com/muzimu217/container-mesh`。
之前不一致导致 `go install ...@latest` 不可用、外部按仓库地址 import 也对不上。
Makefile 里的 `-ldflags -X` 路径同步修改。

## D22. 错误不再静默吞掉

评审指出多处 `_ = SendFrame(...)` / `_ = os.Remove(...)`。影响不是崩溃，而是
**排障困难**：对端只会看到超时或「哈希不一致」，看不到「I/O 错误」。
现在这些路径至少 `log.Warn` 一行；关键路径（发布失败、哈希不符）确保
**一定给对端一个明确的 FileResult**，不让它空等。

# 2026-10-19 第四轮：P2P 直连 + 外部评审第 11 轮修复

## D23. 引入 UDP 直连（打洞），relay 退回"会合点 + 兜底"

**问题**：此前 100% 流量经 relay，延迟下限是 2×RTT（peer→relay→peer）。同一局域网的
两台机器也要绕公网。

**决定**：加 `internal/p2p` 包，用 ICE 式流程建立直连：
1. 双方各绑一个 UDP socket，用 **同一个 socket** 查 STUN 得到 reflexive 候选
   （映射是按 socket 分配的，换 socket 就换端口，候选失效）；
2. 候选经**已加密的会话通道**交换（`FrameP2POffer/Answer`），relay 无法篡改；
3. 双方同时向对方候选打洞（simultaneous-open），收到 punch/punch-ack 即成功；
4. 成功后 `peer.Session.UpgradeToDirect` 把传输换成 `p2p.Conn`，relay 退出数据面；
5. 任何一步失败 → 保持 relay，功能不受影响。

**关键实现细节（都踩过坑）**：
- **conn id 必须两端一致**：初版各自生成 sessionID 并拿它当 `pkt.connID`，
  结果双方把对方的打洞包当杂包丢弃，回环上也永远打不通。改为取两者较小值。
- **切换必须双向确认**：一端切到 UDP 而另一端还在 relay 时，relay 上的在途帧
  被丢弃，AEAD 计数器错位（实测 `decrypt failed at counter 2`）。现在双方都
  收到对方的 `P2PAnswer{OK:true}` 后才切换。
- **读泵要能识别"切换"**：`switchable` 包装层在旧 socket 被关闭时返回
  `ErrTransportSwitched`，读泵继续读而不是判定会话失败。
- **累积 ACK 必须在收到 datagram 时推进**，不能等整条消息重组完成：512 KiB
  消息 ≈ 440 个分片，等重组会让发送窗口永远不释放（实测卡在 2%）。
- **窗口等待用条件变量而非轮询**：2ms 轮询在 440 分片上累积成主要开销。

**诚实结论（性能）**：回环实测 50 MiB / 8.09s ≈ **6.2 MiB/s**，远低于 relay 路径
的 539 MiB/s。直连的价值在于**跨公网降低 RTT 和 relay 带宽成本**，不在于回环
吞吐——回环上 TCP 本来就比这个用户态 UDP 实现快。当前 UDP 实现还有优化空间
（批量写、GSO、更大的 in-flight 窗口），但已在功能上闭环并通过测试。

**未做**：UDP 上的拥塞控制（当前是固定窗口 + 重传）、连接迁移（换网后保持会话）、
IPv6。这三项是后续优化方向。

## D24. 零字节文件传输修复（外部评审第 11 轮）

**报告**：`have == offer.Size` 被同时用来表示"字节数够"和"数据在哪"。

**验证**：复现成功（`mempipe: closed`，接收端 `open : no such file`）。

**修复**：引入 `havePath` 区分两件事，并用 `alreadyFinal = havePath == finalPath`
判断是否真的完整。三处受影响：打开分支、校验来源、发布分支。

**额外发现的同类 bug**（报告未提）：空 `.part` 存在时，`havePath == partPath`
且 `have == 0 == offer.Size`，仍会误判为完整。用 `alreadyFinal` 统一判断后解决。

**测试**：`edgecase_test.go` 四个用例（空文件、覆盖已有空文件、短文件对照、
空 `.part` 续传）+ e2e 三项断言。

## D25. 隐藏文件策略：文档化而非放宽

**报告建议**：写明限制，或加 `--allow-hidden`。

**决定**：只写文档，不加开关。理由：接收端把文件写进工作目录，允许 `.bashrc`
之类是真实的代码执行风险；而传隐藏文件的正当需求（配置、占位文件）可以用改名
或 tar 解决。加开关会让默认安全变成"取决于用户记不记得关掉它"。

## D26. 评审产物目录隔离

评审者上传的 `.go` 文件被 `go vet ./...` 当作本仓库源码扫描，导致构建失败。
`reports/` 现在有自己的空 `go.mod`，Go 工具链把它当独立模块跳过；同时在
`.gitignore` 中排除。报告文件本身移到了模块外的 `../container-mesh-reports/`。

## D27. CI 增加 govulncheck

报告指出 24 项可达漏洞全部来自 Go 1.24.9 标准库（非本仓库代码）。CI 加
`govulncheck ./...`，但**不阻断构建**（`|| echo ::warning::`）——标准库漏洞由
工具链补丁版本决定，`go.mod` 的 `go 1.24.0` 不锁补丁号，正常升级即可修复。
阻断会让"工具链旧"变成"CI 红"，掩盖真正属于本仓库的问题。

## D28. P2P 直连改为默认关闭（实测数据驱动）

**实测**：1 GiB 传输，回环环境

| 路径 | 耗时 | 吞吐 |
|---|---|---|
| relay（TCP over WS） | 2 s | ~512 MiB/s |
| P2P（用户态 UDP） | 79 s | ~13 MiB/s |

**原因**：分片粒度受 MTU 限制（1177 字节/包），每包付出一次系统调用 + 一次
AEAD + 一次锁；relay 路径一次处理 512 KiB。440 倍的固定开销差异盖过了直连
省下的网络跳数。回环上 TCP 本来就极快，UDP 实现没有机会。

**决定**：`--p2p` 默认关闭。保留开关，因为直连的真实价值在**跨广域网**：
RTT 减半、不占 relay 带宽、丢包时不发生 TCP 队头阻塞。但这些收益需要真实
跨公网链路才能评估，本地无法证明。

**不做的**：没有实现"自动测量并选更快的路径"。那需要一条稳定的测量协议、
切换时的处理中数据迁移，以及对路径质量抖动的迟滞策略，复杂度远高于当前的
收益；在真实广域网数据出来之前，让用户显式选择更诚实。

**后续优化方向**（如果直连变得重要）：批量发送（sendmmsg）、更大的
in-flight 窗口、AES-GCM 的批处理、拥塞控制。这些能把 UDP 路径推到百 MiB/s
量级，但属于独立的性能工作项。

## D29. STUN 事务 ID 改用 crypto/rand

`internal/probe/net.go` 此前用 `math/rand` + 时间种子生成 12 字节事务 ID。
可预测的 txid 让**路径外攻击者能伪造 STUN 绑定回复**，把探测结果里的公网地址
换成攻击者选定的值——`probe` 的输出会被用来判断 NAT 类型，伪造会误导部署决策。
RFC 5389 要求 96 位随机性，`crypto/rand` 是唯一正确来源。

## D30. code 未指定时自动生成（采纳报告建议，但理由不同）

报告的出发点是"弱 code 对 relay 可离线枚举"。同意，但补充一点：**要求用户自拟
code 本身就是弱点的来源**——人会选 `test123`。所以不是"提示用户用强 code"，
而是**默认就不给用户犯错的机会**：未指定时用 `crypto/rand` 生成 26 字符
（31 符号表，约 128 位熵），打印一次供对方输入。

字母表刻意排除 `0/O`、`1/l/I`：code 需要人工转录一次，形近字符会造成
"看起来一样但不匹配"的挫败（SPAKE2 会直接握手失败，用户很难自查）。

**未做**：没有强制禁止短 code。`--code` 显式给出时仍按原规则（规范化后 ≥6 字符）。
强制会破坏脚本化用法，而"默认安全 + 显式可覆盖"是更诚实的边界。

## D31. `--force` 与 `--allow-hidden`：显式能力，默认仍安全

报告建议加这两个开关。采纳，但**默认值不变**：

- `--force`：默认拒绝覆盖同名文件（保护本地数据）。开启后用 `os.Rename` 原子替换。
- `--allow-hidden`：默认拒收点开头文件（防止 `.bashrc` 类代码执行风险）。
  开启后**只放开隐藏文件**，路径分隔符、`..`、`.part`、Windows 设备名的拦截
  不受影响（`TestAllowHiddenPolicy` 覆盖了这一点）。

设计原则：安全默认 + 显式覆盖，而不是"可配置所以默认放宽"。用户必须主动
输入一个标志才能降低安全性，这个动作本身就是一次确认。

# 2026-10-19 第六轮：第 14 轮评审（基于最新代码，三条成立）

## D32. 累积 ACK 的排他性（H1）

`handleAck` 把对端通告的 `recvNext` 当作**含端点**处理，于是删掉了一个从未收到的
序号。丢包场景下：接收方通告 `recvNext=N`（表示 N 还没到），发送方却把序号 N 的帧
删了 → 该帧永不重传 → 消息永远拼不完整 → `Recv` 挂死，而 `Send` 早已返回。

修复：`seqBefore(seq, pkt.ack)`（严格小于）。测试 `TestCumulativeAckIsExclusive`
在修复前精确失败（`frame 2 was dropped by an ACK advertising recvNext=2`）。

**为什么之前的测试没抓到**：`TestFragmentationLargeMessage` 在回环上不丢包，
所以永远走不到这条路径。报告指出该用例在他们沙箱里 3/3 稳定失败——**丢包才是
常态，回环是特例**。这也说明本地测试环境过于理想。

## D33. 转发头只在受信代理后采纳（H2）

`clientIP` 无条件信任 `X-Forwarded-For` 最左条目。任何客户端都能每请求编一个新
地址，于是：① 每个请求都拿到新的限速预算（实测 60/60 通过 vs 无头时 5/60）；
② 限速表按声称地址增长，**可远程触发的内存放大**（实测 20000 请求 → 20000 条
记录、约 5 KB/请求）。

修复：新增 `TrustedProxies []string`（CIDR 列表，默认空 = 不信任任何人）。只有
请求确实来自配置的代理时才读转发头，否则以 socket 地址为准。

**默认空是刻意的**：安全默认 + 显式配置，而不是"为了兼容反代而默认信任"。
部署在 nginx/Caddy 后面时由运维显式声明代理地址。

同时补上 `StartMaintenance`——`limiter.sweep` 之前只被测试调用，生产路径从不
调用，等于限速表只增不减。

## D34. parked waiter 死亡检测：三条路线都试过，最后选客户端兜底（R14-M1）

**问题**：relay 的 parked waiter 不读 socket（gorilla 会 latch 读错误），所以
parked 期死掉的 peer 不可见。若 partner 在「同角色新连接顶替」之前到达，
`join` 会把 partner 与尸体配对 → splice 首次读失败 → **两端一起关**，活的那端
收到正常关闭码和零数据。实测复现率 35%（40 轮中 14 轮）。

**试过的三条 relay 侧路线，全部否决**：

1. **读探测（带 deadline 重试）**：实验证明 gorilla 的读错误一旦 latch，
   **后续读直接返回旧错误**（`TestDeadlineThenReadStillWorks` 验证：deadline
   触发后连接被永久污染）。且重试到 1000 次会 panic。
2. **写 ping 探测**：ping 不污染读侧，但检测延迟受 tick 间隔限制。竞态窗口是
   **毫秒级**，把间隔降到 200ms 仍然 14/40 失败，再降就是无意义的空转。
3. **单次读探测 + early 缓冲**：能检测死亡（graceful-close 从 14 降到 0），
   但探针**持有读锁**，splice 排队等它。测试发一次数据时 27/40 超时；只有
   客户端持续发送才正常。**让 relay 的正确性依赖客户端的发送模式是不可接受的**。

**最终方案（客户端兜底，报告推荐的路线 3）**：会话结束时若
`FramesSinceStart() == 0`（除 hello 外没收到任何帧），说明这次配对没有承载任何
数据——立即重试，不走退避。这把「一次多余的延迟」变成「一次透明的重连」。

**为什么这个信号可靠**：hello 交换必然发生（计数器不为 0），所以用**基线差值**
而不是原始计数。修复过程中先用了原始 `RecvCounter() == 0`，测试立刻发现它永远
不成立（hello 就已经是 1）。

**未做**：relay 侧的「回槽」方案（报告路线 1）。它需要按方向统计已转发帧、
处理 PAKE 首帧可能已被消费的情况，改动 relay 状态机。在客户端兜底已经消除
用户可见影响的前提下，不值得为此重写配对逻辑。

## D35. 握手输入校验（F2）：不可信对端 + 第三方库 = 必须自己兜底

恶意 relay 在 WebSocket 升级后回一个**二进制**的 4 字节 `null`，客户端立刻
`panic: invalid memory address or nil pointer dereference`，SIGSEGV、退出码 2。
**不需要知道 code、不需要配对成功**——任何能连上的 relay 都能让所有客户端进程死掉。

根因：`schollz/pake` 把输入 `json.Unmarshal` 成 `*Pake` 后**不做 nil 检查**就解引用。

修复两层：
1. **结构校验**：非空、≤8 KiB、合法 JSON、有 `Role` 字段、至少一个非 null 的
   坐标字段。注意 pake 的实际线格式是 `{"Role":0,"Uᵤ":...,"Uᵥ":...}`（Unicode
   下标字段名），第一版校验按 `S`/`P` 猜字段名，把**正常握手也拒了**——测试立刻
   发现，改成「除 Role 外至少一个非 null 字段」。
2. **recover 兜底**：`pake` 是第三方库，校验若有遗漏不能让进程死。

**顺带确认**：文本帧攻击无效（`wsconn` 只接受 `BinaryMessage`），只有二进制才
进握手路径——这解释了报告作者第一次复现失败的原因。

## D36. 按帧 RTO（F4）：连接级计时器是吞吐杀手

原实现每 25 ms tick **无条件** `c.rto *= 2`，不管这一 tick 有没有真的重传。
于是连接刚建立约 200 ms，RTO 就顶到 `MaxRTO=3s`；第一次丢包要等 3 秒才补，
之后每个丢包再叠 3 秒。报告抓到 `srtt=3.006s` 的伪样本。

修复：`outFrame.rto` 按帧计时，只在**该帧真的需要重传时**翻倍。同时按 Karn 规则，
**重传过的帧的 ACK 不采信 RTT 样本**——否则 3 秒退避会被反馈成平滑 RTT，进而
justify 更长的等待。

配套 F5：`SetReadBuffer/SetWriteBuffer(8 MiB)`。默认收包缓冲约 212 KiB 只装得下
约 180 个数据报，而发送窗口是 512 → 满窗突发必丢。

**实测效果**：512 KiB 消息 **6ms / 88.1 MiB/s**（报告测上游是 2.2–68 MiB/s 双峰，
3 次里 1 次成功）。新增 `TestLargeMessageThroughput` 作为回归守卫（阈值 5 MiB/s，
只拦「慢一个数量级」）。

## D37. 协商失败必须关闭会话（F8）

`readP2PFrame` 超时后弃置一个仍阻塞在 `RecvFrame` 的 goroutine，而随后启动的读泵
会与它**抢同一通道**——被弃置的那个可能吃掉第一帧业务数据。

修复分两处：
1. 明确注释约束：协商是严格串行的，同步读安全；超时后 reader 仍存活，
   **调用方不得启动读泵**。
2. 调用方（`negotiator`）在信令失败时**返回 error 关闭会话**，让 node 重连。

**关键区分**：只有「读 offer 失败」和「信令超时」会传播 error（这两处才有弃置
reader）；打洞失败返回 `nil` error 正常回退 relay。所以 UDP 被完全封锁时不会
陷入「每次协商都断线重连」的循环。

## D38. SAS 强制比对（F9）

`ShortAuth()` 之前只出现在一行状态日志里。既然 RoomID 已经把 code 从 URL 拿掉、
也明确承认「relay 拿得到 label 就能离线猜弱口令」，那么**主动 relay 的唯一真正
防线就是 SAS**——而它是建议性的，一键式 `--stay=false` 用户基本看不到。

新增 `--expect-sas <6位>`：不一致直接中止会话并提示「possible active relay or
wrong code」。默认仍不强制（会破坏脚本化用法），但把它写进 README 的上手流程。

## D39. 未修的两项（F6/F7）——诚实说明

**F6（无 SACK/快重传）**：现在只有累积 ACK，丢一帧要等一个 RTO 才补，且补之前
所有后继帧都被无谓重传（报告实测 449 帧发出、重传 441 次）。补齐 SACK + 快重传
约需 200–300 行 + 测试，属于设计级改动。

**F7（`Send` 语义）**：注释说「阻塞到整条消息被确认」，实现是「入队即返回」；
且重传 12 次后**静默丢弃**该帧且不报错。

**报告建议换 `quic-go`**，我同意这个判断但**本轮不做**：
- 换 QUIC 意味着 P2P 路径完全重写（拥塞控制、重传、流复用都是现成的，但
  candidate 交换、打洞、回退判定要重做）；
- 而 P2P 目前**默认关闭**，且在我们的实测中回环吞吐低于 relay 路径；
- 在「直连是否真的值得」这个问题被真实广域网数据回答之前，投入重写不划算。

**因此本轮只做「不丢、不卡、能回退」**，并把 F6/F7 记录为已知限制。README 已
明确 `--p2p` 是实验特性。

# 2026-10-20 第八轮：真实跨公网 P2P 验证

## D40. 跨公网打洞成功（首次真实环境验证）

**环境**：两台云服务器，`47.108.249.115`（阿里云深圳）↔ `175.24.139.148`（腾讯云，
OpenCloudOS，4 核 3.6G）。

**关键前提**：两台都是**对称 NAT**——`probe` 显示三个 STUN 服务器返回三个不同
端口（如 `175.24.139.148:40418 / :42463 / :46017`）。按经典 NAT 理论，对称 NAT
双端打洞成功率约 20%，**这次成功了**。

**结果**：10 MiB 文件，8 秒，SHA-256 完全一致；两端日志均显示 `p2p-direct`，
接收侧实测 RTT **41 ms**（成都/深圳真实延迟），relay 只承担了信令。

## D41. 常驻模式不应有配对超时（本轮发现的真实 bug）

**现象**：跨公网测试时，`recv --stay=true` 每 60 秒重连一次，日志
`no partner appeared within 1m0s`，relay 侧看到 `replacing parked peer role=B`
反复出现——**它在不断踢掉自己的占位**。

**根因**：`PairWindow` 默认 60s 且对所有模式生效。常驻节点本该一直等，结果每
60s 主动断开重连，把刚建立的 parked 状态销毁，对方永远赶不上这个窗口。

**修复**：`PairWindow = 0` 表示「一直等」，且只在**单 relay** 时生效（多 relay
仍需要窗口才能换线）。一次性命令显式设 25s。

**为什么之前没发现**：本地测试两端几乎同时启动，60s 窗口绰绰有余；只有跨公网
且人为错开启动时才会暴露。这也说明**测试的时序假设过于理想**。

## D42. RTT 测量：没探测过的地址不能算 RTT

打洞时双方**同时**发 punch，所以先到的可能是对方的探测包而不是对我们探测的回复。
旧代码用「第一次探测时间 → 收到包」计算，会得到 1ms 这种假值（47 侧就报了 1ms，
而真实是 41ms）。现在只在**确实向该地址发过探测**时才计算，否则报 0（未测量）。

**影响**：仅影响诊断输出的准确性，不影响连接本身。但错误的 RTT 会误导
「哪条路径更快」的判断，所以值得修。

# 2026-10-20 第九轮：P2P 数据面改用 quic-go（方案 A 验证通过）

## D43. 为什么换掉自研可靠性层

第 15 轮评审已指出「这是一个手写的、比 TCP 弱很多的 TCP」。我用丢包注入测试
（`lossyPacketConn`，不依赖 `tc netem`）量化了后果：

| 场景 | 自研层 | quic-go |
|---|---|---|
| 20 条消息 @ 10% 丢包 | **失败**：消息 8 丢失，消息 9 被当作 8 交付 | ✅ 全部正确 |
| 20 条消息 @ 20% 丢包 | 未通过 | ✅ 通过 |
| 512 KiB @ 10% 丢包 | 未验证 | ✅ 通过 |
| 回环吞吐 | 13 MiB/s | **219.5 MiB/s** |
| 跨公网（47↔175，双对称 NAT） | 10 MiB / 8s | **20 MiB / 7s**，hash 一致 |

**根因**：自研层只有 datagram 级累积 ACK，没有消息级边界。丢一个分片后：
- 接收端把消息 N+1 的 index 0 当成新消息，覆盖 N 的部分重组数据；
- 发送端重传 12 次后静默删帧（`Send` 已返回成功）；
- 上层按顺序读，于是「N+1 的内容出现在 N 的位置」——**应用层看到有效但错误的数据**。

我尝试了 SACK 位图、消息 ID 隔离、失败即断连三套修复，每次都在新的边界情况下
失败。这不是可以靠补丁解决的小问题，而是可靠传输的核心难题。

## D44. 保留两套传输，QUIC 为默认

按「不砍功能」的要求：

```
--p2p           → QUIC（默认）
--p2p-legacy    → 自研层（保留，标注会在丢包下丢消息）
--p2p=false     → relay（默认，完全可靠）
```

自研层保留的价值：**零第三方依赖**。如果某个环境无法引入 quic-go，它仍是唯一
选择——但必须知道它的限制。

## D45. quic-go 接入的两个关键实现细节

**1. QUIC 的流必须写入数据后才会被对端感知。**
`OpenStreamSync` 返回成功不代表对端 `AcceptStream` 能返回——空流不会触发对端的
accept。这导致我的第一版实现永久阻塞。修复：客户端打开流后立刻写一个字节作为
「流已建立」标记，服务端先读掉这个字节再进入消息循环。

**2. 单条双向流，而不是每条消息一条流。**
`AcceptStream` 的顺序**不保证**与发送顺序一致（不同流之间无序）。第一版用
per-message stream，20 条消息的测试立刻发现消息 1 和 2 乱序。改为单条双向流 +
长度前缀分帧后，顺序由流本身保证。

## D46. TLS 在 QUIC 里不是安全边界

QUIC 需要 TLS 证书，但本项目的安全来自上层的 SPAKE2 + AES-256-GCM：
- 双方用共享 code 认证（relay 无法冒充）；
- 所有载荷在进入 QUIC 之前就已加密。

因此 QUIC 的证书是**一次性自签**的，两端都跳过验证。这不是「关闭 TLS 校验」
的安全退化——真正的认证在别处，QUIC 只负责可靠传输。

# 2026-10-20 第十轮：自研可靠 UDP 传输的第二次尝试（`internal/p2p2`）

D43 记录的是「自研层在丢包下会串消息，因此降级为 legacy」。这一轮按
`container-mesh-reports/research-reliable-transport.md` §5 的路线重写了一个新包
`internal/p2p2`，**不修改** `internal/p2pquic`（生产默认）与 `internal/p2p`
（legacy），也**尚未接入 CLI**。完整的逐轮 KPI 记录见
`internal/p2p2/KPI.md`。

## D47. 消息身份成为重组表的第一维

**决定**：每个数据报带 `msgID(4) + fragIndex(4) + fragCount(4) + msgLen(4)`；
重组表 `map[msgID]*reassembly`；交付严格按 `msgID` 顺序推进。

**为什么这一条单独成立**：旧层的 `recvParts map[uint32][]byte` 用**分片下标**做
key，完成条件是 `len(map) == total`。两个缺陷叠加后，消息 N+1 的分片可以填满
消息 N 的洞并凑够数量，于是「消息 9 被当作消息 8 交付」。这不是丢包问题，是身份
问题——SACK、消息 ID、断连三样单独加都修不好（研究文档 §1.4 已逐个论证）。

新层的四条不变量：

1. 分片只能写进自己 `msgID` 的槽；
2. 槽的 `fragCount`/`msgLen` 一旦建立，后续分片必须完全一致，否则丢弃；
3. `msgID < nextMsgID` 直接丢弃（重复抑制）；
4. `nextMsgID` 只在前一条消息 `remain == 0` 时前进，**永远不跳过**。

`fragCount` 还要与 `msgLen` 推导出的片数一致、每片 payload 长度精确匹配，所以
「组装完成」等价于「字节与发送端分片时逐字节相同」，不需要额外的完整性检查。

## D48. 不做消息级 TTL——超时就让连接失败

**取舍**：研究文档 §4.3 提到可选的消息级 TTL。**没有实现**。

**理由**：部分消息超时后如果丢弃它并推进 `nextMsgID`，后续消息会整体错位交付
——这正是旧层 `conn.go:413` 清空 map 继续下一条的做法。如果不推进 `nextMsgID`，
那条消息之后的全部数据都堵死，连接已经不可用。两种情况下唯一诚实的结局都是
**连接失败**，让上层重连或回退 relay。因此 `Send` 的契约是「整条消息被 ACK」，
分片重试超限就 `fail(ErrPeerUnreachable)`，绝不静默丢弃。

## D49. ACK 用 ranges 而不是位图

**决定**：`una(4) + nRanges(1) + n × (gap(2), length(2))`，最多 8 段。

**为什么不是 64 位或 256 位位图**：位图要**和发送窗口一样宽**才可靠。ACK 只能
描述 `una+1 .. una+width`，更上面的到达对发送端不可见，会被误判为丢失。窗口
1024 就需要 128 字节位图，占 1200 字节 MTU 的 11%，而且数据包和纯 ACK 都要付。
实测同一窗口同一丢包模式：固定位图 107 MiB/s，ranges 129 MiB/s。

**截断是安全的**：块永远明确声明 `una`（「这个序号没到」），所以队头洞在任何
截断下都可判丢；被截断的高端只是「没报告」，不会变成「已丢失」。

**段数从 16 降到 8 是实测结果**：每个预留段占 4 字节 payload，而 payload 变小
意味着包数变多，包数在丢包场景下就是重传量。20% 丢包下 32 字节的差异让 512 KiB
从 5.4 MB/s（16 段）变成 13.8 MB/s（8 段）。代价是重窗口深处的报告更粗，表现为
重传次数上升（20% 下 443 → 598），但不会导致卡住或错序。

## D50. 丢包判定的三个坑（都实测过）

RFC 9002 §6.1 的包阈值（3 个后续 ACK）与时间阈值（9/8 RTT）是**或**关系，
不是与。实现时踩了三个坑，每个都有量化后果：

1. **只在与关系下判定**：4 片消息丢 1 片时只有 3 个后续包，包阈值恰好卡在边界；
   若第 3 个 ACK 在重排窗口内到达，这片永远不判丢，只能等 RTO。实测 5% 丢包下
   `rtoFires=6, fast=0`，全部靠定时器修。
2. **只按 `p.sentAt` 算时间阈值**：一次 Send 会把整个窗口在远小于重排窗口的时间
   内打进 socket，于是「比 9/8 RTT 更老」描述了大部分健康突发。实测 0% 丢包下
   每 512 KiB 有 25–38 次伪快重传。加上「必须在 `largestAcked` 之后」后归零。
3. **在 ACK 之外不跑检测**：Send 突发后最后一个 ACK 往往在重排窗口到期前就到了，
   之后不再有 ACK，突发里所有丢失都得等满一个 RTO。把同一判定挂到定时器 tick 上
   后，恢复从 52.3 ms 降到 2.4 ms。

## D51. RTO 下限从 50 ms 降到 5 ms（有效下限 4×RTTick）

**决定**：`MinRTO = 5ms`，实际下限取 `4*RTTick = 8ms`。

**理由**：RFC 6298 的 1 秒下限是为「唯一时间源是粗粒度时钟」的 1980 年代路径写的；
这里 srtt/rttvar 是按包测的。回环 RTT 是 40–60 µs，50 ms 下限相当于 800 倍路径
延迟，每一次尾部丢包都要付满它。实测 5% 丢包：50 ms 下限 4.6 MiB/s，5 ms 下限
21 MiB/s，同一丢包模式。

**代价**：可能出现伪重传。一次伪重传的代价是一个接收端会去重的重复包；白等一个
无谓 RTO 的代价是整条传输的吞吐。Karn 规则保证估计值不会被重传包污染。

## D52. 快重传可以重复，但用 minRTT 节流

**决定**：同一包可以被快重传多次，但距上次重传不得短于
`max(4*minRTT, rto/4, 1ms)`。`MaxRetries = 20`。

**否决的两个方案（都实测过）**：

- **一次性快重传**（KCP 的 `fastresend=1` 形态）：把同一包的第二、三次丢失全部
  交给 RTO。20% 丢包下这是大多数情况，实测 10% 丢包出现 9 秒的 512 KiB 传输。
- **每次 ACK 都重判**：包阈值是单调的（`largestAcked` 只增不减），一旦满足就永远
  满足，于是每个 ACK 都重发一次。实测 20% 丢包 478 片重传 404 次，几何下界是 120。

**节流基准必须是 minRTT 而不是 srtt**：srtt 在负载下增长，而负载正是发生重传的
时候，用 srtt 会形成正反馈——实测 20% 丢包的 512 KiB 在 20 ms 到 92 ms 之间抖动。
minRTT 是无排队传播延迟，不随发送端忙碌而变。

## D53. 三个「定时器被覆盖」的 bug（第 8 轮，最大的一次提升）

同一轮修掉三个都在重传路径上的缺陷，5% 丢包吞吐从 22.6 提到 80.7 MiB/s：

1. **`writeData` 每次传输都重置 `p.rto`**，把 RTO 路径刚做的指数退避抹掉，于是
   同一包在每个后续 tick 都被重发。现在只在首次传输时设置，并且改到
   `enqueueLocked` 里设置——入队与写之间定时器可能已经跑过，看到一个零值
   `sentAt` 会当成「292 年前就该超时」。
2. **退避在原值上翻倍**，永不回落：一个包经历三次 RTO 后带着 8 倍于路径估计的
   定时器过完余生，后面所有丢失都继承这个等待。改成「当前估计 × 2^attempts」。
3. **`timeoutScan` 取「第一个过期的包」而不是队列头**。快重传之后，队列里更靠后
   的包可能是最老的过期包，重传它对 `una` 毫无帮助，而真正的队头要等自己那个
   已经被翻倍过的定时器。实测 10% 丢包因此出现 6 秒传输。

## D54. ACK 批量：乱序到达也延迟

**决定**：只有「完成了一条消息」和「重复包」立即 ACK，其余（含乱序）都批量。

**理由**：一个 ACK 块已经报告了接收端知道的全部 ranges，N 个立即 ACK 与 1 个
携带相同信息。丢包会让后续每个包都「乱序」，于是接收端变成每个数据包回一个 ACK。
实测 5% 丢包下 ACK/数据比 0.98 → 0.13，吞吐 30.8 → 34.9 MiB/s。

**代价**：丢包信号最多延迟一个 `AckInterval`（2 ms），远小于它替代的 RTO，也
小于丢包判定本来就要等的重排窗口。

## D55. 不做的与已知限制

**明确不做**（研究文档 §5.2 P3）：多路复用、连接迁移、0-RTT、ECN、FEC、
基于带宽估计的 pacing。（拥塞控制最初列在这里，第 14 轮已实现，见 D61–D65。）

**已知限制**：

1. **回环吞吐受限于 syscall，不是协议**。0% 丢包下 76% 的 CPU 在 `rawsyscalln`：
   每个约 1131 字节数据报一次 `WriteTo`，464 个数据报 × ~10 µs ≈ 4.6 ms，正好是
   实测时间。要突破需要 `sendmmsg` 批量发送，那要拿 raw fd 并做平台分叉
   （`x/sys/unix` + build tag），属于独立工作项。当前 145–165 MiB/s，已超过 100 MiB/s
   的目标。
2. ~~没有拥塞控制~~。**第 14 轮已实现 Reno**，`SendWindow` 降为窗口上限、默认开启，
   见 D61–D65 与本文件 D62 的下限论证。残余限制是 Reno 的 RTT 偏差：公平性从「饿死」
   改善到「有份额但不等分」，真正等分需要 CUBIC 或速率型控制器。
3. **pacing 是「窗口摊到一个 RTT」的简化形态**，不是基于带宽估计的 pacing。
   它在回环上是 no-op（slot 低于 1 µs），在长 RTT 路径上才起作用。
4. **ACK 截断到 8 段**。极端随机丢包（20% 下窗口内约 200 个洞）会让低端 ranges
   被截断，代价是重传次数上升（实测 443 → 598），不会误重传也不会卡住。
5. **未接入 CLI**。`peer.Session` 仍然走 `p2pquic`；`p2p2` 目前只有包内测试。
   接入需要一层 `MessageConn` 适配与开关，属于下一步。

# 2026-10-20 第十一轮：批量发送突破 syscall 瓶颈（`internal/p2p2`）

D55 把「0% 丢包下 76% 的 CPU 在 `rawsyscalln`，每个数据报一次 `WriteTo`」列为已知
限制，并指出突破方式是 `sendmmsg` 批量。这一轮把它做掉了。逐轮 KPI 见
`internal/p2p2/KPI.md` 的 Round 13。

## D57. 首次发送批量，重传不批量

**决定**：`Send` 的首传按 `Config.BatchSize`（默认 32）攒批，一次 syscall 发一批：
Linux 用 `sendmmsg(2)`，Darwin 用 `sendmsg_x(2)`。重传（快重传、RTO）仍然一包一次
`WriteTo`。

**为什么重传不批量**：这是本设计里最重要的一条取舍。重传路径是丢包 KPI 的全部
来源（D50–D53 四轮修的就是它），而重传的数据报在序列空间里是散落的、不连续的，
攒批既没有顺序保证也省不了多少 syscall（丢包场景下重传量只占总量一小部分）。
把批量限制在「一条消息的连续首传」上，丢包路径的代码一行没动，所以 5%/20% 的
KPI 是**结构上**不会退化的，不需要靠调参证明。实测确认：5% 与 20% 与各自 A/B
基线相比都在噪声内（75.1 → 75.8、26.4 → 33.3 MiB/s best-of-31）。

**顺序如何保证**：一批永远是同一条消息的连续升序分片；`sendmmsg` 和 `sendmsg_x`
都按数组顺序发送；短返回（内核只发了前 n 个）表示「前 n 个已发出」，所以尾部
重新提交而不是当成错误。`batchQueue.write` 的循环就是这条契约，测试
`TestBatchQueueResubmitsTailAfterShortReturn` 用假 writer 直接钉住它。

**`x/sys/unix` 没有 `Sendmmsg`**：v0.39（本仓库锁定版本）既没有 `Sendmmsg` 也没有
`Mmsghdr`，所以 `mmsghdr` 结构体和 syscall 包装都在 `batch_linux.go` 里自己声明，
`SYS_SENDMMSG` 从 `unix` 取。结构体布局用**编译期断言**钉住（`batch_linux_64.go` /
`batch_linux_32.go` 里的常量数组边界）：64 位 `msghdr` 56 字节 / `mmsghdr` 64，
32 位 28 / 32。布局一旦漂移就是构建失败，而不是内核里读到垃圾指针。

## D58. 平台分叉与回退：`batchWriter` 接口 + 可选 `batchSender`

**决定**：平台相关的只有「一次 syscall 发 N 个」这一件事，藏在 `batchWriter`
接口后面（`writeBatch` + `maxBatch`）。`batch_linux.go` / `batch_darwin.go` /
`batch_other.go` 各提供一个 `newBatchWriter`，其余（攒批、短返回、计数、回退）都在
平台无关的 `batch.go` 里，只有一份。

**`Conn` 仍然接 `net.PacketConn`**：批量需要 raw fd，所以定义了可选的
`batchSender` 接口（`SyscallConn() (syscall.RawConn, error)`），`*net.UDPConn`
天然满足。不满足的连接 `batcher` 为 nil，发送路径走逐包 `WriteTo` —— 不是另一条
代码路径，而是同一条路径上 `q == nil` 的分支。

**包装器必须能拦住批量**：这是正确性问题，不只是测试问题。`harness_test.go` 里的
`lossyPacketConn` 内嵌 `*net.UDPConn` 并重写 `WriteTo` 来注入丢包；如果不管它，
传输层会把内嵌的 `*net.UDPConn` 断言成 `batchSender`、直接对 socket 做批量写，
**绕过 `WriteTo` 也就绕过了丢包注入**，所有丢包测试都会在一条无损路径上通过。
所以加了 `batchProvider` 接口：包装器返回自己的 `batchWriter` 就保留在链路里，
返回 nil 就表示「我这个包装不支持批量」。测试用的 `lossyBatchWriter` 走前者，
对每个数据报做同样的掷硬币，并报告整批已发送（丢掉的包是「发送方交出去了、网络
丢了」，与逐包 `WriteTo` 的语义一致）。

**运行时回退**：对端地址如果不是 `*net.UDPAddr`（例如 Unix domain），批量写返回
`errBatchUnsupported`，`batcher` 被清空，**已攒的这批仍然逐包发出去**——它们已经
在发送队列里、已经占了序号，丢掉只会让它们等定时器。这条路径由
`writeBatchData` 的 `q == nil || c.batcher.Load() == nil` 分支处理。

## D59. 批量大小默认 32

**决定**：`DefaultBatchSize = 32`。

**依据**（0% 丢包，交错测量，每档 best-of-15）：1→89.4、4→171.0、8→185.2、
16→201.5、**32→218.5**、64→213.5、128→218.6 MiB/s。另一轮 8/16/32/64 的独立扫描
给出 78/85/93/85 MB/s，排序一致。

16 以上是平台期：收益是「每次 syscall 的开销被摊薄」，16 个已经摊到噪声以内。
选 32 而不是 16 是因为再砍一半 syscall 数而实测无代价；不选 64/128 是因为它们
没有更好，而更大的批会让一批里的第一个数据报等更久（批要攒满或 Send 结束才发）。
小于一批的消息不受影响：`Send` 在最后一个分片后立即 flush，由
`TestBatchSmallMessagesNeverFillBatch` 覆盖。

## D60. 这一轮的 KPI 与代价

| KPI | 逐包基线 | 批量 | 变化 |
|---|---|---|---|
| 512 KiB @ 0%，best-of-31 | 101.0 MiB/s | **209.5 MiB/s** | **2.07×** |
| 512 KiB @ 0%，中位数 | 80.5 MiB/s | **186.4 MiB/s** | 2.31× |
| 512 KiB @ 5%，best | 75.1 MiB/s | **75.8 MiB/s** | 噪声内 |
| 512 KiB @ 20%，best | 26.4 MiB/s | **33.3 MiB/s** | 1.26× |
| 消息顺序 20 条 @ 0/5/10/20% | 100% | **100%** | 不变 |
| race | 0 | **0** | 不变 |

464 个数据报从 464 次 syscall 变成 15 次（size=32）。单独给 `Send` 计时（对端
socket 抽干、不经过协议接收端）是 6.01 ms → 2.69 ms，2.24×，与端到端 0% 的数字
一致，这是「syscall 地板真的移走了」的直接证据。

**没有达到 250 MiB/s 目标**。剩余成本大致对半分：批量发送 syscall 占 CPU 37%，
而**接收端**的逐包 `ReadFrom` 循环占 38% —— 这一轮没有动接收路径，它仍然是一个
数据报一次 `recvfrom`。同样的回环微基准里，只算发送侧能到 ~320 MB/s，所以
209 → 250 之间挡着的是批量接收（`recvmmsg` / `recvmsg_x`），那是下一轮的事，
不在这一轮的范围内（本轮只改发送路径）。

**踩到的一个真 bug（值得记）**：第一版在 `waitForWindow` **之后**才 flush。
只要窗口小于批量上限就会死锁——批里的数据报已经占了序号、已经算进 `inFlight`，
但没人写它，于是窗口永远腾不出来：能让窗口腾出来的数据报正躺在缓冲区里。默认
配置（窗口 1024、批量 32）把它藏住了；而同一时期在做的拥塞控制初始窗口是 10，
一上来就踩中：模拟 4 MB/s 链路上实测 0.02 MiB/s，每十个分片等一个 RTO。修法是
**阻塞前先 flush**，但只在窗口真的满时 flush，否则等于放弃批量。回归测试
`TestBatchWindowSmallerThanBatchDoesNotDeadlock` 用窗口 2/4/10 对批量 32 钉住。

**代价**：任何丢包率下都没有可测的吞吐代价；每消息的额外延迟上限是「编码一批
分片」的时间。没有改协议、没有改窗口、没有改 ACK 策略，所以 D47–D54 的全部结论
不受影响。

## D61. 拥塞控制选 Reno，不选 CUBIC

**决定**：实现简化版 Reno（RFC 5681）——慢启动 + 拥塞避免 + 快恢复 + RTO 降窗。
`SendWindow` 从「工作窗口」变成「窗口上限」，实际在途数由 `cwnd` 决定。默认开启，
`Config.DisableCongestionControl` 可关闭以做 A/B。

**为什么是 Reno 而不是 CUBIC**：CUBIC 的价值在高速长肥管道（cwnd 很大时用三次函数
恢复窗口），而这一层的窗口以「数据报个数」计、上限 1024，对应约 1.2 MB 在途——远
没到 CUBIC 与 Reno 拉开差距的区间。CUBIC 还需要保存上一次拥塞窗口和到达时间，多
两个状态量与一套浮点立方根运算，收益在这个窗口尺度上测不出来。Reno 的状态机只有
`cwnd`/`ssthresh`/恢复点三个量，且与已有的「包阈值 + 时间阈值」丢包判定天然对齐：
那个判定给出的就是「一个洞」，正好是 Reno 的减窗信号。

**窗口按数据报而不是字节计**：除了消息最后一片，每个数据报都是 `MaxPayload`
字节；发送路径本来就在数数据报（`SendWindow`、`inFlight`）。改成字节会让每个判定
多一个单位而没有任何收益。

**整数运算**：拥塞避免的 `+1/cwnd` 用 `credit` 累加器表示（单位 `1/cwnd`），一个
被确认的数据报加 1 点 credit，攒满一窗换一个数据报的窗口。用 float64 会在取整时
丢掉一个 RTT 的增量——慢启动看起来「永远不涨」，这是个很难发现的静默 bug。

## D62. 窗口下限 128，不是 1

**决定**：`ccMinWindow = 128`（并受 `SendWindow` 截断）。RTO 把窗口压到下限，慢启动
从下限重启。

**两个来源**：

1. **快重传需要后续包**。丢包判定要求 3 个后续到达，窗口接近该阈值时任何一次丢失
   都只能等 RTO。实测：下限 8、回环 5% 丢包，吞吐从 52.6 掉到 5.2 MiB/s（−90%）。
2. **窗口就是「这条路堵不堵」的采样量**。随机丢包的路径上，小窗口几乎每个 RTT 都
   会丢一个，把每次丢失都当拥塞的控制器会把自己永久钉在下限。128 个数据报时一次
   随机丢失只是窗口的一小部分，减窗才是在响应**丢失率**而不是「存在丢失」。

## D63. 三个「一次拥塞事件只降一次」的规则

单个拥塞窗口产生的丢失信号是一串，不是一条。三条规则各自对应一个实测的塌陷：

1. **减窗间隔 ≥ 一个 srtt**。一个 ACK 可以同时宣告多个洞丢失，重排定时器还会每个
   tick 重判同一个洞。不限间隔时实测 200 ms 内减窗 13 次，cwnd 从 512 掉到 12。
2. **在下限上不再因 ACK 判丢而减窗**。见 D62 第 2 条；RTO 仍然任何窗口都生效，因为
   超时意味着 ACK 时钟停了，随机丢包解释不了。
3. **ssthresh 从「本轮峰值」算，且一轮只降一次**。一次丢失风暴会让每个卡住的队头各
   触发一次 RTO；每次都对已减小的窗口再折半，实测把 ssthresh 从 512 打到 8，之后
   整个传输都在「阈值 8」的拥塞避免里爬。

## D64. 顺带修掉的两个重传路径缺陷

两个都不是拥塞控制引入的，但都只在窗口变小后才暴露：

1. **`waitPacing` 可能死循环**。睡眠分支既推进 `nextSend` 又睡掉 deficit，于是循环
   永远能找到新的欠账、永不返回。此前所有配置的 slot 都低于 `minPaceSleep`
   （1024 窗口 / 50 µs 回环 = 49 ns），永远走不到该分支；8 个数据报 / 2 ms RTT 是
   250 µs，正好踩中，表现为传输挂起而不是变慢。
2. **`timeoutScan` 的「推后定时器」会制造假 RTT 样本**。被推后但没有重传的包，
   `sentAt` 晚于真实离队时间，它的 ACK 会报出比路径更短的往返。一个这样的样本把
   `minRTT` 从 41 ms 拉到 50 µs，重排窗口与重传节流随之崩塌，2 MiB 传输以
   `ErrPeerUnreachable` 失败。现在这类包标记 `clockSkipped`，与 Karn 规则排除重传
   样本同理。

## D65. 默认开启，以及代价

**决定**：默认开启。`DisableCongestionControl` 保留为 A/B 开关和逃生门。

**回环（不能退化）**：0% 与 5% 不变或更好（166.5 → 166.4、72.4 → 75.5 MiB/s）；
20% 三次扫描区间重叠（24.8–27.8 vs 27.7–31.7），差异在机器自身波动内。

**模拟拥塞（必须改善）**：4 MB/s、20 ms、256 数据报缓冲、512 KiB 消息。固定窗口
丢包 31.0%、208 次重传、208 次 RTO、吞吐 0.01 MiB/s；拥塞控制丢包 0.0%、0 次重传、
0 次 RTO、吞吐 2.55 MiB/s。固定窗口在这里不是「慢」，是病态：每次重传都加入一个已
经满的队列，于是又被丢掉。

**公平性**：两条流共享瓶颈，5 ms 与 25 ms 单向延迟。固定窗口三次运行的吞吐比
3.74:1、65.43:1、66.71:1（两次把长 RTT 流饿到 0.02 MiB/s）；拥塞控制 0.82:1、
0.07:1、0.59:1——饿死消失，但**没有收敛到 1:1**，且两次越过 1 反向偏移。

**已知限制**：Reno 有残余 RTT 偏差，窗口按 ACK 增长，长 RTT 流单位时间涨得慢。
要真正收敛到等分需要 CUBIC 或基于速率的控制器（BBR 类），不在本轮范围。这一条
必须与「饿死消失」分开陈述，否则会高估本轮的结果。
